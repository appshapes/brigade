# Decisions made on 2026-08-30 after the plan's first review — ALL of them apply and override the plan where they conflict

Guiding principle (user): the tool must just work out of the box — empowering by default, security by opt-in; defaults allow, gates are settings.

- D3 filesystem adapter + conformance suite: YES (now written in Go).
- D32 hosted Supabase project: after the proof (Phase 5).
- D6 join limiter: keep as designed. D31: CI never runs the LLM proof runs.
- D18 inbound policy: `team_inbound` default `accept` in EVERY permission mode and entrypoint, including bypassPermissions, auto and `claude -p` workers. `refuse` (never inject, never ack) is an opt-in setting in v1. `hold` (pending file, held notice, release) is deferred to Phase 5 as the opt-in security feature; its release path is NOT a model tool: the human runs `brigade inbox release` in their own terminal and the watcher injects the released messages. Everything that never blocks stays on: the harness's own peer-message preamble, the `<brigade-message>` frame text, the sanitiser, dedupe, loop/rate bounds, the crossSessionInbound warning.
- D20 outbound: `require_send_confirmation` default `off`; `on` is an opt-in implemented as a documented `permissions.ask` rule `Bash(brigade send*)` (the permission-modes page says explicit ask rules still prompt even where bypass permissions are available, and deny rules block in every mode — an E0 experiment verifies the ask rule in a real bypass session). The skill declares `allowed-tools: Bash(brigade:*)`. No `auto` value.
- D22 roster: every active member can see the whole roster (`list_members` callable by members; `memberships_select` team-scoped). Rotate/revoke/transfer stay creator-only (Phase 5).
- D33 platforms: native Windows is NOT supported; Windows users use WSL 2 (Linux). Drop named pipes, DPAPI, `.cmd` handling, P5-8. Targets: darwin/arm64, darwin/amd64, linux/amd64, linux/arm64.
- D34 model interface: NO MCP server. The model uses the `brigade` CLI through the Bash tool. The plugins reference documents `bin/`: "Plugin executables added to PATH — invokable as bare command in Bash tool". Skill written in the playwright-cli style (commands + rules). Frame reply instruction becomes: `brigade send <session_id> --reply-to <message_id> <<'EOF' … EOF`. Message bodies travel on stdin (quoted heredoc) or `--body-file`, never argv. Every command has `--json`; default output is human-readable, sanitised, stable. Session identity for the CLI: `CLAUDE_PID` is present in the Bash tool environment (verified live in this session), so the CLI reads the hook-written per-PID session map; no `process.ppid` trick. Remove: TeamListSessions/TeamSendMessage/TeamReleaseHeld, `.mcp.json`, MCP SDK, `${user_config}` env plumbing, `_meta["anthropic/requiresUserInteraction"]`, E0-8's MCP sub-items.
- D27 → D35 language: ALL GO (harness CLI, hooks, watcher, default Supabase adapter, fs adapter, conformance suite). TypeScript, npm, esbuild, zod, node --test, ESLint, Prettier, `plugin/dist/*.js`, Node version checks and `engines.node` all go away. One multi-call static binary `brigade` (CGO_ENABLED=0): `brigade sessions|send|whoami|team …|profile …|inbox …` for humans and the model; `brigade hook session-start|prompt|session-end` for hooks; `brigade watch` for the watcher; the bundled Supabase adapter as a hidden subcommand (e.g. `brigade adapter supabase <group> <verb>`) that the harness spawns as a CHILD PROCESS, so the adapter protocol remains a real process boundary and third-party adapters remain separate executables selected by the `adapter_command` option. Dev-only binaries: `brigade-adapter-fs`, `brigade-conformance` (built, never shipped). The Supabase client is hand-rolled on `net/http` + `github.com/coder/websocket`: GoTrue anonymous sign-up, refresh, global sign-out; PostgREST RPC with the `brigade` schema headers and PostgREST error JSON; a minimal Phoenix-channels client for exactly one private broadcast channel (join with `private: true` + access token, heartbeat, `access_token` refresh push, rejoin with backoff). The realtime-js and auth-js sources are the reference specification. `supabase-community` Go libraries may be evaluated but are not assumed (they are thin: no anonymous sign-in, no private-channel authorization documented). Realtime stays a wake-up hint; the polling drain is authoritative. A supabase-js adapter is a FUTURE first alternative adapter (bun-compiled if ever bundled) — not in scope.
- Distribution: GitHub Releases built by goreleaser from tags; the plugin ships a POSIX-sh bootstrap in `plugin/bin/brigade` that, on first use (SessionStart hook or a Bash call), downloads the version pinned by the plugin into `${CLAUDE_PLUGIN_DATA}/bin/`, verifies a committed sha256 (`plugin/bin/checksums.txt`), installs atomically and `exec`s; afterwards it execs the cached binary directly (few ms). Dev override for local builds (`--plugin-dir` + a pointer file or env accepted ONLY from the user's own settings, never from a repository). Humans use the same binary in their terminal (the SessionStart context line prints the path once; symlink into ~/.local/bin; `go install` for developers; Homebrew tap later). Nobody but the developers can install until the first tagged release; the proof runs from local builds.
- Everything else in the plan stands: protocol v1 (section 4) unchanged; Supabase SQL (section 5) unchanged except the D22 roster policy and the adapter internals; the logical plan's freeze/do-not-freeze lists and ten success criteria unchanged; commit rules unchanged (master, merges only, `15: …`).
