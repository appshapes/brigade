## The drain, and why it is not a `seq` watermark

Item (e) is phrased "`drain()` by `seq`", which invites exactly the bug plan 5.7 forbids. The drain is therefore
built the way 5.7 specifies: **page `fetch_inbox` (the `delivery_state = 'accepted'` set) in batches, acking each
page**, with no client-side cursor and no `seq > last` watermark. `seq` orders rows *within* a page and nothing more.

This is not a theoretical distinction — the run observed the inversion 5.7 warns about. **Cross-page drain order went
backwards in `seq`**: once in the verified run (largest step 1), once in the baseline run, zero times in a third. A
lower `seq` committing after a higher one was already visible is precisely the case that would make a `seq > last`
cursor skip a row permanently. Exactly-once held in every run because the cursor is the accepted set, not the
watermark. Recorded, not asserted, since the frequency is timing-dependent.

## (e) 50 concurrent senders — exactly-once holds

50 distinct sender principals and sessions (verified by set cardinality on both uid and session_id, not by
construction), 200 messages to one recipient, released from a single barrier.

- **Concurrency measured, not assumed.** Peak **50 `send_message` RPCs in flight simultaneously**; 50 sequential
  senders would peak at 1. All 50 goroutines issued their first send within 1 ms of each other.
- **The drain raced the senders.** All 26 `fetch_inbox` pages (200 of 200 envelopes) were yielded *before the last
  send returned*, inside the 297 ms burst — so exactly-once is measured under real read/write contention, not against
  a settled table.
- **Exactly-once.** 200 sent, 200 drained, 200 distinct; 0 duplicates, 0 missing, 0 unexpected. Ids are recorded
  *before* the ack, so a lost ack surfaces as a duplicate rather than vanishing.
- **Database cross-check as a set, not a count.** The row-id set for the recipient session equals the sent set, and
  every row is `delivery_state='injected'`. A count comparison would have let one lost row and one stray row cancel.
- **Broadcast order is unordered**, as expected: 29 of 199 consecutive pairs arrived out of `seq` order. Recorded.
- Broadcast coverage was 200/200 in all three runs.

## (f) The "first subscription received nothing" race — not reproduced

Recorded, never a flip. 20 attempts, each on a fresh recipient session and a fresh socket, with four messages per
attempt across four timing classes.

| When the message committed | Broadcast arrived |
| --- | --- |
| Before the socket existed | 0 / 20 |
| During the join handshake | 4 / 20 |
| Immediately after join ok | **20 / 20** (min 0 ms, median 2 ms, max 4 ms) |
| 1 s after join ok (control) | 20 / 20 |

**The strict race — a message sent after join ok being silently dropped — did not reproduce.** What is 100%
reproducible is the pre-join window: anything committing before the join completes is never broadcast, which is
exactly why drain-on-join-ok exists. The drain covered all four messages on 20/20 attempts, in all three runs.

Two things make the negative result trustworthy rather than vacuous:

- **The window was genuinely entered.** Reclassifying the 80 sends by when `send_message` actually *returned* rather
  than by intended class, **40 of 80 committed strictly after join ok**, and none of those missed a broadcast. So the
  clean result rests on ~120 real opportunities across three runs, not on a window that was never exercised. The
  "during handshake" class turned out to commit a median 1–2 ms *before* the join reply, which corrected the author's
  own initial characterisation of that row.
- One unexplained observation is recorded honestly and **not** claimed as a reproduction: in an early warm-up run
  (the process's first socket), five messages landing 10–20 ms after join ok produced no broadcast while the next
  five did. The shape did not recur in three later runs, two of them 200-message runs at 100% coverage.

## (h) Revocation takes effect — on both paths

Tested twice, because `leave_team` both revokes the membership *and* closes the sessions, which would confound the
result. The second variant sets `brigade.memberships.status='revoked'` by direct SQL and leaves the session **open**,
isolating the membership clause of `brigade.owns_session_topic`.

For each variant:

1. **(h)(1)** the next join of the principal's **own** topic is refused `Unauthorized` after the server's fixed
   5 s refusal backoff, on a fresh socket with a freshly refreshed JWT.
2. **(h)(2)** an **already-open** channel is brought down by the next `access_token` push, in 2–3 ms, with
   `system status="error" message="You do not have permissions to read from this Channel topic: …"`.

The controls are what make this conclusive, and all were added during verification:

- **Positive control** — the victim joins its own topic and receives a broadcast *before* revocation, so the
  mechanism is shown to work before it is shown to stop.
- **Committed-state assertion** — the membership row really is `status='revoked'` at the moment of the test (and for
  the SQL variant, `closed_at` is still open, confirming the isolation held and `owns_session_topic` returns false
  purely on the membership clause).
- **Token validity** — `GET /auth/v1/user` with the victim's JWT returns 200 with a matching `sub` and a future
  `exp`, ruling out an expired token as the cause of the `Unauthorized`.
- **Non-member baseline** — the refusal is **byte-identical** to what a principal with no membership anywhere near
  the team is told on that same topic. It is the authorization refusal, not an unrelated error containing the word.
- **Server-health control** — an untouched active member still joins its own topic `ok` at that same moment, so the
  refusal is this principal's revocation and not a realtime server that had stopped authorizing everybody.

## Why this suite is trustworthy

The author's first draft passed everything it asserted. Adversarial review then found **15** ways a check could pass
for the wrong reason — more than the 7 found in E0-1 — and all were fixed before this result was recorded. The most
consequential:

- **The exactly-once detectors were never shown capable of failing.** Three self-tests now inject real faults into a
  dedicated fixture: a row forced to `injected` behind the drain's back (what a silently lost delivery looks like to
  `fetch_inbox`) is caught as a shortfall; a row forced back to `accepted` after being yielded (a lost ack) fires the
  duplicate detector with exactly one entry; an unacked row is noticed by the database cross-check. Without these,
  "0 duplicates, 0 missing" over a fault-free run proved nothing about the comparison itself.
- **"50 concurrent senders" was asserted by construction only.** Fifty goroutines serialised by an HTTP transport
  limit would have produced identical output. Now measured as peak in-flight RPCs.
- **Completeness compared against whatever survived.** If the rate limiter had truncated the run to 40 messages,
  "sent 40, drained 40, missing 0" would have passed while no longer testing 50 senders. The intended total is now
  re-required at the comparison.
- **Nothing established the drain ran while the senders wrote**, so exactly-once might have been measured against a
  static table.
- **(f)'s timing classes named intent, not measured behaviour**, so a negative result could have described a window
  never entered.
- **(h) printed the post-revocation database state but never asserted it**, matched the refusal with a substring
  containing "Unauthorized", and had no control proving the realtime server was still authorizing anyone.
- **The soak was vacuously satisfiable**: `i-delivery` asserted `len(drained) == sent`, trivially true when
  `sent == 0`. And because the drain has a 5 s safety timer, a broadcast path that died at minute one of thirty would
  still have left it green — the soak was a test of *polling*, not of broadcast. It now asserts a workload floor,
  a broadcast floor of 80% of sends, and that broadcasts were still arriving at the end.

No migration defects were found in either pass; no schema file was touched.

## Handed to Phase 2 and 3

- The drain is the reference implementation for the watcher's catch-up (6.6, 5.7): page `fetch_inbox`, ack per page,
  never a `seq` watermark. The cross-page `seq` inversion observed here is the empirical justification.
- The `access_token` push is the revocation-propagation mechanism for an open channel and it is fast (2–3 ms). The
  Phase 5 revocation-lag work (I-16 lag) can build on that number.
- The 5 s refusal backoff on an unauthorized join is a server-fixed cost; anything polling joins must budget for it.
- A message committing before a subscription completes is **never** broadcast. Any code path that subscribes and then
  assumes it has seen everything is wrong; drain-on-join-ok is mandatory, not an optimisation.
