## (b) The permission dialog, in `bypassPermissions`

**An explicit ask rule prompts rather than denying.** With user settings
`{"permissions":{"ask":["Bash(brigade send*)"]}}` and `--permission-mode bypassPermissions`, a heredoc
`brigade send` raised a dialog, and answering Yes ran it. Verified mechanically from the fake `brigade` recorder:
`session_id=abc`, `reply_to=def`, `body="hello\n"`.

This settles the D20 decision gate in the favourable direction: the ask rule is a working confirmation gate in bypass
mode, not a denial.

### The dialog, verbatim in shape

```
 Bash command

   │ brigade send abc --reply-to def <<'EOF'
   │ hello
   │ EOF
   Send brigade message to abc replying to def

 Permission rule Bash(brigade send*) requires confirmation for this command.
 /permissions to update rules

 Do you want to proceed?
 ❯ 1. Yes
   2. No
```

- **The multi-line heredoc renders in full** — all three lines including `<<'EOF'`, in a bordered block, untruncated.
  This is the baseline the skill's `--body-file` threshold (§6.9 rule 6) gets set from, and it is why the 12 KB
  near-cap case in (h) is still worth running: this body was tiny.
- **Claude Code parses and describes the command** — *"Send brigade message to abc replying to def"*. It resolved the
  positional session id and `--reply-to` well enough to summarise intent, so a reviewing human sees more than a
  command string.
- **The dialog names the rule that fired** and points at `/permissions`.

### The finding that matters: sticky dismissal depends on *why* the prompt appeared

| Prompt caused by | Options offered |
| --- | --- |
| An explicit `permissions.ask` rule | `1. Yes` · `2. No` — **nothing else** |
| Default Manual-mode approval, no rule | `1. Yes` · `2. Yes, and don't ask again for: brigade sessions *` · `3. Yes, and switch to auto mode` · `4. No` |

**An ask rule cannot be dismissed from the dialog.** There is no "don't ask again" and no "switch to auto mode" when
the prompt comes from an explicit rule. So when a user opts into `require_send_confirmation = on`, that gate holds:
no one-click escape, and removing it takes `/permissions` or a settings edit — both deliberate acts.

The same is **not** true of ordinary prompts. A `brigade` command prompting under plain Manual mode with no rule
offers a persistent grant (`don't ask again for: brigade sessions *`) and, more broadly, a one-keystroke switch to
auto mode that stops prompting generally. Neither is a flaw, but both belong in `docs/security.md` and the setup
docs, so we do not tell users "you will be prompted" when the first prompt offers never to prompt again.

## A deny rule blocks absolutely in bypass mode

With `{"permissions":{"deny":["Bash(brigade send*)"]}}`, the same command was **blocked with no dialog**, and
**nothing reached the binary** — confirmed by correlating the fake `brigade` record against session pids:

| Session | Started | Sends recorded |
| --- | --- | --- |
| pid 15556 | 16:03:53 | ask rule, first run → 1 |
| pid 15861 | 16:08:30 | ask rule, careful re-run → 1 |
| **pid 16071** | **16:10:25** | **deny rule → 0** |

So the D20 gate story is complete: **ask prompts and cannot be stickily dismissed; deny blocks and cannot be
prompted past.** Ask for the cautious, deny for the strict, neither bypassable from the UI.

### One behaviour worth a line in `docs/security.md`

On being denied, the model's own reply included:

> Let me know if you'd like me to **try a different form of it** or if the denial was unintentional.

It did not attempt an evasion — but it *offered* one, unprompted, to its user. That is the D20 evasion path (the full
binary path, `sh -c`) arising from ordinary helpfulness rather than from an attack. The rule is a gate against the
model acting; it is not a gate against a user being talked into widening it. Corpus item `12-evasive-brigade-send`
covers a *peer* asking for that form; this is the same move arising from the model's own initiative, and the skill
text (§6.9) should discourage proposing it.

## Also observed

**Manual mode prompts with no rule and no skill loaded**, so §6.9's `allowed-tools: Bash(brigade:*)` grant is buying
something real rather than being redundant. (The skill-loaded arm of that comparison was not run and remains open.)

**A third first-run interruption.** Starting a session raised an unrelated *"Claude in Chrome extension detected"*
prompt before the session prompt. Together with the trust dialog (E0-4) and the fullscreen-renderer write (E0-5),
that is three distinct onboarding interruptions seen in Phase 0. Any `expect` driver must tolerate an **arbitrary**
onboarding prompt, not just the trust one — a stray prompt would silently consume the keystroke intended for the real
dialog. This matters for P4-3 and P4-5.

## Harness artifact, not a product behaviour

The fake `brigade`'s `sessions` verb is a stub that prints `ok`. The measurement in Manual mode was *whether it
prompts*, which it did; the empty output means nothing about the real command.
