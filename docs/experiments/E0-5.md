# E0-5 — Detached watcher lifecycle, `/clear`, and the SessionEnd budget

Date: 2026-08-31 · Ticket 15 · Status: **closed; two design defects found, one anomaly unresolved** ·
Driver: `scripts/experiments/E0-5/`

This is the experiment that changes the most. **Both of the watcher's specified exit conditions are wrong**: one
never fires when it should, the other fires when it must not. Everything else — `/clear`, the SessionEnd budget, the
`--resume` interleave, the start-token guard — behaved as hoped, and D9's respawn logic is safe.

## Results at a glance

| Check | Result |
| --- | --- |
| (a) survives interactive exit | **PASS** — `ppid=1`, own pgid, own session id, directly observed after exit |
| (b1) exits ≤5 s of `CLAUDE_PID` death | **FAIL** — 27.6 s and 59.0 s measured; **1.04 s once the corpse is reaped** |
| (b2) exits ≤5 s of socket removal | Exits in 1.47 s — **but the condition itself is a false positive** |
| (c) `/clear` | Clean boundary; **socket and token BOTH unchanged**; exactly one watcher; post delivered |
| (d) SessionEnd close inside budget | **PASS** — 0.103–0.110 s, ~14× inside the 1 s cap |
| (f) `--resume` of a live session | Interleaves into the original transcript; `--fork-session` does not |
| (h) plugin `timeout: 5` raises the budget | **NO for a plugin — YES for a settings file** |
| (i) start-token guard | **PASS**, both arms, and reproduced |

## Defect 1 — SIGKILL is invisible to the watcher

`kill(pid, 0)` **succeeds on a zombie**, and a SIGKILLed `claude` stays a zombie until its parent reaps it. Every
one of the plan's signals keeps saying "alive":

```
PID  PPID STAT STARTED                      COMMAND
75159 75158 ?Es  Mon Aug 31 10:19:29 2026     (2.1.251)
  kill(pid,0) -> True    ps -o lstart= -> 'Mon Aug 31 10:19:29 2026'    socket_present -> True
```

`ps -o lstart=` still returns the original start time, so the start-token guard matches. The socket file is left on
disk, so the ENOENT condition never fires. `SessionEnd` does not run at all. **A watcher built exactly to spec sits
there until something else reaps the corpse** — measured at 27.55 s and 58.96 s in two runs. Force the reap and
detection is prompt: 1.042 s to detect, 1.060 s to exit, well inside one 2 s poll.

Section 6.6 anticipates this ("`kill(pid, 0)` keeps succeeding on an unreaped zombie, which cannot happen in
production…") and dismisses it as a test artefact. **The dismissal is too confident.** The latency is not a property
of the watcher at all — it is a property of whoever reaps the corpse, and the distribution of that delay across real
terminals, multiplexers and IDE hosts is unmeasured. The fix is cheap and does not depend on the answer: read the
process *state* so a zombie reads as dead, rather than trusting `kill(pid, 0)` alone.

## Defect 2 — socket-ENOENT is a permanent false positive

The watcher detects an unlinked socket promptly (1.468 s, one poll interval) and closes cleanly. The problem is that
it should not treat that as a death at all:

- **`claude` never re-creates the socket.** Newly measured: unlinked with the session provably alive, polled every
  25 ms for the remaining 16.08 s — it never reappears, not at exit, not afterwards.
- **The session keeps working normally without it.** So a watcher that exits on ENOENT has killed itself for a live
  session, permanently, with no recovery.
- **The path is not an independent signal anyway.** It is `/tmp/cc-socks/<claude_pid>.sock` — derived from the pid,
  so it tells you nothing the pid check does not already.

A `connect()` probe would be a real liveness test. `os.path.exists` is not.

## (c) `/clear` — D9's respawn path is safe, and cold

`SessionEnd(reason=clear)` then `SessionStart(source=clear)`, 37–40 ms apart, **same `CLAUDE_PID`, new native session
id**, exactly one watcher surviving. The crux for D9:

**Neither `CLAUDE_CODE_MESSAGING_SOCKET` nor SHA-256(`CLAUDE_CODE_MESSAGING_TOKEN`) changes across `/clear`.**

Confirmed three times, including once in a run with no watcher in the picture at all. A post made after `/clear`
using the **startup** coordinates — the ones the watcher is holding — was delivered, reaching the model 25 ms later
under the new session id. So D9's hash-compare-and-respawn is correct either way, but the respawn branch is **cold**:
nothing in `/clear` or `/resume` triggers it.

`/resume` behaves identically in-process — and adds a fact that matters for the by-native map: **a native session id
can recur within one process** (`99a48c02 → /clear → d2c72366 → /resume → 99a48c02`). A map keyed on native id must
tolerate the same id reappearing rather than assuming ids are monotonic.

`/fork` is **not a boundary in this process at all.** It spawns a separate background `claude` with its own pid,
socket, token, session id and transcript; the original carries on with no `SessionEnd`. The pid-keyed spawn routine
correctly produced a second watcher. `/fork` is therefore the *only* observed thing that exercises D9's respawn path,
because it is the only one that changes the pid.

## (d) and (h) — the SessionEnd budget

The close is comfortable: **0.103–0.110 s against a 1 s cap**, about 7% of the whole SessionEnd budget, across 18
runs. With a deliberately slow adapter the cap fires at 1.0015–1.0021 s and the lease expires cleanly, with roughly
0.5 s of budget still unspent.

Check (h) was `[uncertain]` in the plan and now has a two-sided answer, from arms whose `bin/` trees are
byte-identical (`diff -r`) and differ only in the `timeout` field:

| Declared in | `timeout` | Allowance measured |
| --- | --- | --- |
| plugin `hooks.json` | none | 1.5002 s (median, n=6) |
| plugin `hooks.json` | `5` | 1.5033 s (median, n=5) |
| plugin `hooks.json` | `60` | 1.4991 s (median, n=3) |
| `--settings` file | `3` | **3.00 s** |
| `--settings` file | `5` | **5.00 s** |

**A plugin cannot buy itself more SessionEnd budget; a settings file can.** The hooks page does not draw this
distinction and §3.8 should. The session-end hook therefore keeps its 1 s cap, exactly as the plan's fallback said.
Note also that the budget is one *shared* wall-clock deadline across all SessionEnd hooks running in parallel.

## (f) `--resume` of a live session interleaves

`claude --resume <native id>` while the original is alive succeeds, and the two processes write into **one
transcript**: 34 of 35 records in session A's file carry A's id, with B's user turn and assistant turn among them.
The second process does get its own pid, its own socket, its own registry entry and its own watcher pidfile.

`--fork-session` does **not** interleave — the forked session wrote its own transcript and A's file was byte-for-byte
unchanged across it.

This is exactly the situation the `session_live` guard of 4.5.8 refuses and the hook's live-pidfile check of 6.3
avoids, and it is now demonstrated rather than assumed.

## (i) The start-token guard works — with a caveat about cleanup

Both arms, reproduced: an **unedited** pidfile for a live watcher is judged alive and left alone (same inode, no
second watcher); the **same** pidfile with a forged `start_token` is judged dead and replaced. The control arm is
what makes this discriminating — a routine that always replaced would pass without it.

**But the replace path leaves the superseded watcher running**, and that watcher's own cleanup would delete the
pidfile which by then belongs to its replacement. Compare-then-delete before unlinking a pidfile is therefore not
optional, it is required for correctness.

**Unfixed limitation:** `ps -o lstart=` has 1-second granularity, so PID reuse *inside one wall-clock second* is
undetectable by the guard — six processes were observed sharing one token. No cheap fix is available on macOS.

## Corrections the plan needs

1. **6.6** — replace `kill(pid,0)` with a check that reads process *state*, so a zombie reads as dead.
2. **6.6** — drop `os.path.exists(socket)` as an exit condition. It is a permanent false positive and is not
   independent of the pid check. Use a `connect()` probe if a socket-level signal is wanted.
3. **6.6** — compare-then-delete before unlinking a pidfile (see (i) above).
4. **3.8** — a plugin-delivered SessionEnd hook gets ~1.5 s and cannot raise it from its own `hooks.json`; only a
   settings file can. State this explicitly.
5. **6.3** — `SessionEnd` cannot be the only path that closes a session: it does not fire at all on SIGKILL, and on
   `/exit` it fires ~0.5 s *before* `claude` actually exits, with the watcher pidfile still present.
6. **D9** — the by-native map must tolerate a native session id **recurring** within one process.
7. **9.6 config protection** — the plan's list (settings.json and the two CLAUDE.md files) does not cover what these
   runs actually touch: `$CLAUDE_CONFIG_DIR/history.jsonl` gains a line per typed slash command,
   `$CLAUDE_CONFIG_DIR/projects/` gains a transcript directory per project, and `/fork` creates daemons.

## Still unsettled

- **A `/clear` boundary that leaves no hook records.** In two runs the native session id moved while *neither*
  `SessionStart(source=clear)` nor `SessionEnd(reason=clear)` was recorded. The benign explanations were killed by
  two discriminator runs (an idle session that types only `/exit` keeps one id; a `/clear` immediately followed by
  `/exit` still produces all four records). **Unresolved, and it matters**: if a boundary can pass unobserved, a hook
  that assumes it will see every boundary can miss one. Worth carrying into P3-x.
- **Socket recreation was measured on a `claude -p` session only.** An interactive session might re-bind on some UI
  event that `-p` never reaches.
- **The `/resume` boundary has n=1.** Three other attempts never reached it (empty picker, or a modal swallowing the
  post).
- **The `/fork` second watcher** was verified by pidfile and liveness evaluation, not by a process listing — the
  census filters on the run's primary claude pid, so a forked child's watcher never appears in it.

## Harness hazards worth knowing

- **Claude Code disabled its own fullscreen renderer config-wide.** After two expect-driven sessions failed to start
  the fullscreen renderer on a bare pty, Claude Code wrote `fullscreenAutoDisabled` into `$CLAUDE_CONFIG_DIR/.claude.json`
  — a setting that affects the *user's own* sessions, not just the experiment. It was reverted, and independently
  verified absent afterwards. Any future pty-driven experiment should expect this and check for it.
- A `SessionStart` hook that spawns the watcher must be fast and must tolerate being killed partway — two runs lost
  their watcher to the hook timeout.
- Every wait in an `expect` driver must be built out of `expect`; a sleep-based wait fails intermittently.

## Verification

The adversarial pass found eight weak points, six fixed. The two most valuable:

- **(b) had no null control.** Every (b1)/(b2) latency was reported without a run in which *neither* trigger fired —
  so a watcher that simply self-terminated after ~30 s would have produced the same numbers. Two 130 s null arms were
  added: the watcher stays alive, and a code read confirms `detach.py`'s only exits are `claude_gone`,
  `socket_enoent` and the `O_EXCL` abort. No timer, no max-life.
- **Socket recreation was unmeasured** and the author flagged it themselves. It is now measured, and the answer made
  (b2) worse rather than better — turning a possibly-transient condition into a permanent false positive.

Two figures are honestly caveated rather than repaired: the `--reap` arm's `t0` is when the non-reaping parent was
killed, not when the kernel actually reaped, so 1.042 s is an upper bound; and the `/fork` second watcher was not
confirmed by `ps`.
