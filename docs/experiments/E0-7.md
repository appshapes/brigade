# E0-7 — Two sessions, two profiles, one config directory

Date: 2026-08-31 · Ticket 15 · Status: **closed; all items pass** · Harness: `scripts/experiments/E0-7/`

Two concurrent `claude -p` sessions in **one** `CLAUDE_CONFIG_DIR`, each selecting a different Brigade profile
through its own `--settings` file:

```json
{"pluginConfigs": {"brigade@inline": {"options": {"profile": "alpha"}}}}
```

Profile resolution works exactly as designed. The plan's "debug profile resolution" fallback is not needed.

## Results

| Item | Result |
| --- | --- |
| 1. Both register under their own profile | **PASS** — one registry file per profile, no cross-writes |
| 2. `brigade whoami` names its own profile from the Bash tool | **PASS** — resolved through the by-pid map, proven |
| 3. Each `brigade sessions` shows the other | **PASS** — with a hard overlap barrier |
| 4. Does a fresh `CLAUDE_CONFIG_DIR` inherit the login? | **No.** Recorded for P5-10 |

## Item 2 is the one that matters, and it was proven properly

The Bash tool never receives `CLAUDE_PLUGIN_*` variables, so a `brigade` command run by the model can only learn its
profile by resolving `CLAUDE_PID` through the by-pid map the SessionStart hook wrote. The harness proved that with a
**map nonce**: the hook mints a random token and writes it *only* into `state/by-pid/<pid>.json` — never into an
environment variable, a settings file or a prompt. A value `brigade` prints can therefore only have been read from
that file.

```
alpha's Bash tool, brigade whoami --json:
  "profile": "alpha", "claude_pid": "10248", "map_nonce": "MAP-A82542AE",
  "profile_source": "by-pid map file (NOT the environment)"
```

Two live in-session negative controls make the claim falsifiable rather than decorative:

- **Poisoned environment.** `CLAUDE_PLUGIN_OPTION_PROFILE=bravo` set in the environment while the map said `alpha` →
  `whoami` answered **alpha**. The environment value is ignored; the map wins.
- **Missing map entry.** `CLAUDE_PID` pointing at a pid with no map entry → `brigade: cannot resolve this session`,
  exit 6. So a hardcoded or defaulted answer would have failed.

Independently corroborated: the model ran `printenv CLAUDE_PLUGIN_OPTION_PROFILE` in each session and got exit 1 with
no output, so the witness does not depend on the experiment's own binary. `CLAUDE_PID` *is* present — it is the one
hook-independent handle the CLI has.

## Item 3 used a hard overlap barrier

Registry files left behind by two sequential sessions would satisfy "each sees the other" without the sessions ever
coexisting. Each session's first command was therefore `brigade wait-peer 90`, which blocks until a peer of the same
team under a *different* profile is both registered `live` **and** answers `kill(pid, 0)`:

```
alpha: "peer online: profile=bravo pid=10249 (I am alpha)"
bravo: "peer online: profile=alpha pid=10248 (I am bravo)"
```

Both then listed two live sessions, each seeing the other, with `registered_under` (the registry directory the row
came from) equal to the row's own `profile` in every case.

## Item 4 — a fresh `CLAUDE_CONFIG_DIR` does **not** inherit the login

Recorded only; **no login was attempted**, since that is the user's interactive action.

- **Headless:** `CLAUDE_CONFIG_DIR=<fresh> claude -p "…"` exits 1 after 0.5 s with exactly
  `Not logged in · Please run /login`. It fails fast — the timeout was never approached. The fresh directory is still
  populated with `.claude.json`, `backups/`, `projects/<slug>/<uuid>.jsonl` and `sessions/`, and that `.claude.json`
  has **no `oauthAccount` key** and `hasCompletedOnboarding` unset.
- **Interactive:** opens full first-run onboarding — "Welcome to Claude Code v2.1.251" → "Let's get started." → the
  seven-entry theme picker.
- **Keychain credentials are scoped per config directory**, one item per directory.

So P5-10 must document a one-time `claude login` per config directory. That a single login is *sufficient* is
inferred, not measured — only the negative was observed.

## A correction the verification pass caught in this experiment's own reporting

The measurement stage reported, as a surprise, that `/Users/rjae/.claude-ifthen` is "the one config dir with **no**
keychain credential item at all." **That is false.** The predicted service item
`Claude Code-credentials-3b363050` exists (exit 0, account `rjae`, created 2026-08-29 — before the probe). **All**
config directories have per-directory items. The claim is struck, and it is worth recording that it was caught by
re-deriving the keychain service name rather than by re-reading the prose.

A second, smaller correction: the plan names `/Users/rjae/.claude-ifthen` as "this user's real config dir". The
directory actually in use is `/Users/rjae/.claude-thinktech` — `.claude-ifthen` belongs to the *planning* session.
The plan should read `CLAUDE_CONFIG_DIR` at run time rather than naming either.

## The substantive new finding: the by-pid map is an unauthenticated trust boundary

The poison control is the proof, and its implication runs the other way from the pass. `brigade` takes **both the
profile and the team** out of `state/by-pid/<pid>.json`, and it does so *in preference to* the environment. That is
correct by design — it is the only path available to the Bash tool — but it means **anything able to write that file
decides which profile and which team a session acts as.**

The file is written by the hook into `${BRIGADE_STATE_DIR}` with 0600, so the boundary is filesystem permissions
alone. This is not a defect found in the code — there is no code yet — but it is a property P3-3 and P3-5 must be
written knowingly against, and it belongs in the threat model beside T4. Worth noting alongside it: plugin options
reach **all three** lifecycle hooks (SessionStart, UserPromptSubmit, SessionEnd), reconfirmed across nine firings, so
a teardown path can attribute a close to the right profile from the option *directly* and need not trust the map.

## The environment strip list is short by three more

E0-4 found `CLAUDE_CODE_BRIDGE_SESSION_ID` missing from the plan's eight-name list. Stripping by prefix here removed
**eleven** variables, three of which the list does not contain:

- `CLAUDE_CODE_BRIDGE_SESSION_ID`
- `CLAUDE_EFFORT`
- `AI_AGENT` (not even `CLAUDE_`-prefixed)

The enumerated list should be replaced by the prefix rule everywhere it appears (9.6, 7.4), keeping only
`CLAUDE_CONFIG_DIR`.

## Honest limits

- **Both runs used `claude -p`.** Two-profile behaviour in *interactive* pty sessions is unexercised, and E0-5 showed
  pty-driven sessions provoke behaviour headless ones do not.
- The plugin was loaded with `--plugin-dir` and selected by the settings key `brigade@inline`. Whether a
  `--settings` `pluginConfigs` block selects a profile the same way for a **marketplace-installed** plugin is
  untested.
- `process_alive` is `os.kill(pid, 0)`. It correctly separated a live decoy from pid 999999, but **PID reuse is
  untested** — a recycled pid would make a dead session look live. This is the same hazard E0-5 measured for the
  start-token guard, where `ps -o lstart=` has only 1-second granularity.
- The probe's team filtering is done **in-process** by the fake `brigade`, which walks every profile's registry
  directory. That is a property of the harness, not of the design: in the real system the server enforces isolation
  through RLS, which E0-1 verified live (byte-identical `unauthorized`, `42501` on every foreign object).
- That one `claude login` makes a fresh config dir usable is inferred, not measured.
