# E0-6 — Token refresh coexistence, the `session.json` flock, and the in-memory refresher

Date: 2026-08-31 · Ticket 15 · Status: **closed; all six checks pass, with three plan corrections** ·
Driver: `scripts/experiments/E0-6/`

A 30m28s soak with `jwt_expiry = 300` and **three real OS processes** sharing one `profiles/default/session.json`:
a long-lived writer holding a Realtime channel, a short-lived CLI starting fresh every 20 s, and a sandboxed process
under a real `sandbox-exec` profile that cannot write and therefore refreshes in memory only.

All six checks pass. But three of the six were originally carried by instruments that could not have failed, and one
of the plan's stated server rules turns out to be wrong.

## The headline correction: two-behind does **not** revoke the family

Plan 5.1 states as measured fact that "a token two or more steps behind revokes the family
(`refresh_token_already_used`)". **That is wrong for GoTrue v2.196.0 as configured here.** Reproduced in all three
runs and then independently on a throwaway principal, with more than 12 s between every step so the 10 s reuse
dedup cannot explain it:

| Token presented | Answer |
| --- | --- |
| One step behind | **HTTP 200**, carrying the *active* token |
| Two or more steps behind | **HTTP 400** `refresh_token_already_used` |
| The active token, one second later | **HTTP 200**, rotating normally |

**The stale token is refused; the family survives.** This is materially better than the plan assumes, and it changes
error handling: 5.1 currently treats `refresh_token_already_used` as re-read-once-then-*terminal*, where terminal
means clearing `session.json` and telling the user to run `brigade team join` again — a new principal. Since the
family is intact, the re-read-and-retry path will normally succeed, and going terminal on the first failure would
destroy a working credential unnecessarily.

## The lock is fine; the poll interval is not

The soak reported 7,897 lock acquisitions, median 0.006 ms, max 0.179 ms, **all uncontended**. That measurement is
worthless, and the verifier caught why: the contention prober ticked at 250 ms while the refreshers ticked at 1 s and
3 s, all started within 250 ms of each other. Commensurate periods fix the relative phase, so the probe landed
106–133 ms after every acquisition and **could never fall inside the ~45 ms hold**. Zero contention was structurally
guaranteed, not rare — a distribution of zeros is evidence of *no contention*, not of a fast lock.

Re-measured with two jittered refresher processes racing one file:

| | |
| --- | --- |
| Contended acquisitions | **23 of 80** |
| Contended wait | min 100.2 ms, median 101.1 ms, **max 303.1 ms** |
| Time the lock is actually held | **36 ms** (median refresh round trip) |

**Contention costs whole poll quanta.** The design's `LOCK_NB` polled every 100 ms rounds any contention up to a full
poll interval, so a contended waiter pays ~100 ms to wait out a 36 ms hold. The cost is the poll interval, not the
holder. The plan's own fallback — "keep the lock but make it blocking without the 10 s bound (P2-6)" — is the right
call, and this is the measurement that justifies it. Either block on a goroutine with a 10 s timeout, or drop the
poll to 5–10 ms; either roughly halves the cost.

The 10 s `unavailable` bound was never approached in the soak (0 of 7,897), so it was separately proven live rather
than left as dead code: a holder took the lock for 13 s and the waiter returned `unavailable` as specified.

## One-behind tolerance is load-bearing, not a convenience

Checks (d) and (f) turn out to be the **same mechanism**, and the plan should say so.

The SIGKILL in (d) was aimed, not lucky: a third process's `flock(LOCK_EX|LOCK_NB)` returned `EWOULDBLOCK`
immediately before the kill, and the victim's marker read `refreshed-holding-lock`. So the victim had **already
rotated `22ce5485 → edb2f5b1` server-side and died before the atomic write**. That rotation was lost from disk.

The profile recovered only because, 90 s later, the long-lived process presented the stale file token and GoTrue
answered one-behind with the active one. **Without one-behind tolerance, any crash between the refresh answer and the
atomic write would strand the profile.** That makes it a correctness property of crash recovery, not a nicety.

The kernel releases `flock` on process death — the lock was free again **1.651 ms** after the SIGKILL, and the other
processes made 620 further authenticated RPCs with no lockout.

## Two more facts worth recording

- **PostgREST allows ~30 s of clock skew past `exp`.** Measured: HTTP 200 up to 30 s past expiry, `PGRST303` from
  31 s. A JWT-expired answer is therefore not a precise expiry signal, and the 90 s margin has more headroom than it
  looks.
- **Only one of 5.1's two refresh triggers can fire in normal operation.** The 90 s margin keeps every token at least
  90 s from `exp`, so the reactive "refresh after a `PGRST303`" path never runs while a process is alive and ticking.
  It is a cold-start / long-sleep / clock-jump path only. It is implemented and was verified working when forced —
  keep it, but the plan should say what it is actually for.

## The six checks

| Check | Result |
| --- | --- |
| (a) zero `refresh_token_already_used` | **PASS** — 19 refreshes, all HTTP 200; corroborated server-side in `auth.refresh_tokens` (9 rows, 8 rotations, chain intact, 1 live) |
| (b) both processes always hold a valid token | **PASS** — 0 `PGRST303` across 1,888 authenticated RPCs and 90 separate short-lived process lives; smallest margin exactly the design's 90 s |
| (c) file never torn, 0600, lock fast | **PASS on integrity**, corrected on timing — 732,916 lock-free reads, 0 parse failures, 0 missing fields, mode 0600 on every read, 0 stray temp files |
| (d) kill mid-refresh does not lock others out | **PASS** — kill proven inside the critical section; lock free 1.651 ms later |
| (e) channel survives refresh and restart | **PASS** — 8/8 `access_token` pushes; after a 22 s full-stack outage the channel rejoined unaided and drained everything queued |
| (f) in-memory refresher never breaks the family | **PASS** — 11 clean one-behind redemptions, 0 breakage |

The sandboxed process is worth a note: under a real `sandbox-exec` profile denying `file-write*` on the profile
subpath, both its write probe and its `CreateTemp` probe failed with "operation not permitted", and it persisted zero
times across the soak — yet it could still take `flock(LOCK_EX)` on the sidecar through an `O_RDONLY` descriptor, so
it honours the lock protocol despite being unable to write. It also cannot chain itself ahead of disk, because it
always *presents* the refresh token currently in the file.

## Verification found the decisive flaw again

Ten weak points, eight fixed. Beyond the lock-contention flaw above:

- **(b) rested on an untested premise.** The whole check assumed `brigade.list_members` is refused with `PGRST303`
  on an expired JWT. If that RPC had been callable by `anon` or without an `Authorization` header, 1,888 HTTP 200s
  would have proved nothing. The premise was then tested and holds.
- **(c)'s torn-read detector had no positive control**, and its power was misattributed: a read can only tear *during
  a write*, so the real sample size is the 8 file rotations, not 732,916 reads. The detector was then shown to fire
  on a deliberately truncated file.
- **(e) was instrumented client-side only.** `access_token_push ok=true` recorded merely that a websocket write
  returned `nil`, and "channel still up" read the client's own flag. Realtime sends no `phx_reply` to an
  `access_token` message, so the harness was structurally incapable of detecting a rejected push. Re-proven from the
  server side.
- **(a) rested on 8 rotations** from the harness's own log; it was corroborated independently from
  `auth.refresh_tokens` and strengthened with 80 forced refreshes from two racing processes.

## Honest limits

- **The soak's one-behind path was manufactured by a margin asymmetry** — the sandboxed process ran a 150 s margin
  against the writers' 90 s — rather than arising from the design. The independent boundary probe is the real
  evidence; the soak's 11 redemptions are corroboration, not proof.
- **Which process wins a refresh cycle is a phase accident** of the tick periods, the same class of artefact as the
  contention flaw. At real margins the long-lived writer won all 8; in a compressed run the 20 s CLI won all 4.
  Neither ordering is a property of the design.
- **Crash recovery was demonstrated at exactly one point** in the write path (after the refresh answer, before the
  atomic write). A kill during the rename itself, or during the directory fsync, is untested — which is precisely
  where the atomic-write design earns its keep.
- The two-behind stranding scenario is reasoned from two separately verified facts; an actual double-crash was not
  staged.
- The (e) restart used `docker stop`/`docker start` on the five containers. The stated reason (that the Supabase CLI
  is unavailable) is wrong — it is reachable as `npx supabase` — but the substitution is harmless and arguably
  harsher, since it removes the whole backend.
- One accounting nit: 64 messages were sent, 63 broadcast and 63 drained. The 64th was sent at the instant the
  children were signalled to stop — a teardown race, not a lost message.
