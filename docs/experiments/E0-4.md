# E0-4 — Idle-wake automation

Date: 2026-08-31 · Ticket 15 · Status: **closed, criterion MET** · Driver: `scripts/experiments/E0-4/`

**A frame posted to the inbox socket of an idle `claude` session produces a new assistant turn, with nothing written
to stdin. 12 of 12 delivered runs woke, worst case 6.7 s against a 10 s budget.** This is the mechanism the whole
watcher design (6.6) rests on: it is how a teammate reaches a session that is sitting there doing nothing.

## The criterion, and how it was proven

Plan section 8: run `claude -p --input-format stream-json --output-format stream-json --verbose --plugin-dir <probe>`,
and after the first result post a frame to the session's socket while no stdin is pending. Pass = a new assistant turn
on stdout within 10 s. Additionally proven with a recorded interactive run driven by `expect`.

| Mode | Runs | Woke | Latency (post → first visible model output) |
| --- | --- | --- | --- |
| `-p` stream-json | 7 | 7/7 | 3114, 3157, 3162, 3585, 3724, 4342, 6682 ms — median 3585, max 6682 |
| interactive (`expect`) | 5 | 5/5 | 1534, 1664, 1718, 1916, 2847 ms — median 1718, max 2847 |

Interactive is consistently *faster* than `-p`. Seventeen nested sessions were run in total and all are accounted
for: 12 delivered runs (all woke), 3 correct negatives, and 2 that aborted before any post. None were discarded.

**The number 6.6 should actually budget against is much tighter.** Everything above is dominated by model latency.
The part the harness controls — enqueue to delivery inside the receiving session — was **1–7 ms in every one of the
12 runs**. When a session is idle the queue drains essentially instantly; there is no polling interval to wait out.

## The controls are what make this a result

Three negatives, one of which had to be added during verification and is the decisive one:

- **Null post (the causation control).** Identical flags, stdin open, the socket confirmed present on disk at the
  instant a post *would* have been made, child alive, 30 s idle hold plus 60 s observation. **Zero stdout events,
  zero further transcript records, no wake.** Without this, "an idle session spontaneously emitted a turn" was not
  excluded by experiment. The original two controls could not do this job, because in both of them the session had
  already exited and its socket was unlinked, so the poster never even dialled.
- **No `--input-format stream-json`.** The session exits at its first result; there is nothing left to wake.
- **stdin closed (EOF) right after the prompt.** Same outcome. Differing from the passing runs only in this, it
  isolates **the open stdin as the load-bearing condition**: it is what keeps the session alive-but-idle rather than
  finished.

## Ruling out the ways this could have been wrong

- **Wrong session.** The nested socket, token and session id are published by the *nested* process's own SessionStart
  hook and compared against the outer session's before anything is posted; the driver **refuses to post** on any
  match, so a leak aborts the run instead of producing a fake pass. All 12 nested sockets differ from the outer
  `/tmp/cc-socks/29130.sock`, and each nested `CLAUDE_PID` equals the PID the driver actually spawned.
- **Not actually idle.** The idle gap was recomputed from each *receiver's own* transcript rather than the driver's
  belief: 3.04 s to 120.04 s, with zero records and zero stdout events throughout. The long holds matter — a 30 s and
  a 120 s hold both woke, which rules out a race with the just-finished turn.
- **stdin not quiet.** stdin was wrapped in a logging class and `proc.stdin` is touched nowhere else but `.close()`;
  every run logs exactly one write of 112 bytes before the first result, and nothing after.
- **Coincidence.** The woken turn carried that run's unique per-run nonce, and the model used the frame's
  `reply-to-session-id` and `message-id` — values that exist nowhere but inside the frame.
- **Flattered latency.** The stopwatch starts at the poster's *completed* socket write (after connect, auth, frame,
  close) and stops at the first assistant event. Two earlier signals were available and deliberately not used:
  `command_lifecycle` fires 3–5 ms after the post, and thinking tokens 1.4–2.2 s before the assistant event.

## Two `expect` facts worth reusing in P4-3

The trust dialog was answered on the record, and it took two failures to get right. Both are recorded because P4-3's
interactive fallback will hit them:

1. **A bare Enter is the wrong answer.** The highlighted default is "No, exit", so Enter *quits* the session. The
   correct sequence is Down-arrow then Enter to select "Yes, I trust this folder".
2. **Multi-word regexes never match.** The dialog is drawn as a box, so cursor-positioning escapes fall between the
   words. Match on a single word.

A third point applies to any interactive measurement of injected content: **an interactive session renders the frame
on screen**, so a marker appearing verbatim in the frame would also appear without the model doing anything. The
marker is therefore split — the frame asks for `WOKE` followed by a 4-hex tail and never contains the concatenation,
and the driver aborts before spawning if the joined token leaks into the frame. This trap does not exist in `-p`,
where stream-json never echoes the injected frame at all.

## A correction to the plan's environment-strip list

9.6 and 7.4 specify unsetting eight variables (`CLAUDE_PID`, `CLAUDE_CODE_SESSION_ID`,
`CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDECODE`,
`CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_EXECPATH`) before running a nested session.

**`CLAUDE_CODE_BRIDGE_SESSION_ID` is also exported by an outer session and is not on that list.** It caused no
contamination here — the nested session minted its own `bridgeSessionId` — but the list is documented as exhaustive
and is not. The scripts of 9.6 and the `env -u` recipes of 7.4 should either add it or switch to stripping
`CLAUDE_CODE_*` as a prefix, which is robust against the next variable to appear.

## Honest limits

- **One build, one machine, one account, one ~40-minute window** (Claude Code 2.1.251, Darwin). No cross-version or
  cross-platform evidence that socket-injected frames dequeue on an idle session.
- **Every nested session ran with `--permission-mode bypassPermissions`.** Idle wake under a normal permission mode is
  untested. The wake itself precedes any tool use so is very likely unaffected, but the woken turn's `brigade send`
  would prompt.
- **The longest proven idle is 120 s.** A real watcher implies a session parked for hours; nothing here tests token
  expiry, socket reaping, connection staleness or context compaction over that horizon. That gap belongs to E0-5.
- A bare socket connection with auth and *no* user line was not separately tested as a wake trigger. Not needed for
  the criterion — the content evidence is conclusive — but relevant if 6.6 ever wants a cheap liveness ping.

## Two figures the author reported that verification corrected

Recorded because the writeup should not quietly absorb them: one interactive latency was quoted as 1508 ms where the
run's own `verdict.json` says 1534 ms, and the claim that `ps` showed state `S` in 40/40 samples is true of the 30 s
run but does not generalise — a 120 s hold sampled 158 times and saw both `R` and `S`. `ps` state is weak evidence of
idleness for a Node process in any case; the authoritative evidence is the transcript silence, which is unaffected.

## Handed on

- 6.6 can rely on socket-post wake with a harness reaction of single-digit milliseconds; the seconds in the table are
  the model thinking, not the queue.
- The **open stdin is the load-bearing condition** for a `-p` session to remain wakeable. A worker that closes stdin
  after its prompt cannot be reached, which is a documentation point for 6.11.
- E0-5 inherits the long-horizon question: does a session parked for hours still wake, and what expires first?
