## Ordering constraint discovered before any check ran

**With `brigade` listed in `[api] schemas`, `supabase start` cannot succeed until a migration creates the schema.**
Starting the stack with an empty `supabase/migrations/` leaves PostgREST looping on

```
Failed to load the schema cache using db-schemas=public,graphql_public,brigade …
{"code":"3F000","message":"schema \"brigade\" does not exist"}
```

until the CLI gives up with `supabase_rest_brigade unexpected status 503` and tears the whole stack back down. The
plan's E0-1 ordering — init → config → **migrations** → `start` — is therefore a hard requirement, not a preference.
Worth a guard in `make supabase-start` (P1-1): a fresh clone is fine because the migrations are committed, but any
workflow that empties or reorders `supabase/migrations/` will hit this and the error names PostgREST, not the cause.

## Check (a) — the ported live checks: 72 assertions, 0 failed

Driven through the research round's Go client over raw HTTP with the profile headers. Grouped by property:

| Group | Assertions | Result |
| --- | --- | --- |
| `setup` — anonymous sign-in role, fixture distinctness | 2 | pass |
| `a1` — team isolation on every table, incl. the D22 roster | 12 | pass |
| `a2` — server stamping and the impossibility of client-supplied identity | 9 | pass |
| `a3` — uniform `not_found`, foreign vs unknown session id | 12 | pass |
| `a4` — publishable-key-only requests | 2 | pass |
| `a5` — secret-key / `service_role` requests on tables | 3 | pass |
| `a6` — `join_team` unknown team | 2 | pass |
| `a7` — revoked membership | 11 | pass |
| `a8` — `list_members` non-member | 2 | pass |
| `i` — per-function revokes (below) | 17 | pass |

Specifics worth keeping:

- **Isolation (a1).** A principal in team A sees exactly its own rows in `teams`, `memberships`, `sessions` and
  `messages`, and zero rows of team B. A principal in no team gets HTTP 200 with `[]` on all four — an empty result,
  not an error, so membership is not an existence oracle. The roster is visible to every active member, creator or
  not (D22). `select *` on `teams` is `42501` even for a member, because the column-level grant excludes
  `secret_hash`; the adapter must name columns. `join_attempts` is `42501` for everyone.
- **Stamping (a2).** Direct `INSERT`/`UPDATE`/`DELETE` on `messages` and `sessions` is `42501` for members — there
  are no write policies, so RPC-only holds. Passing `sender_user_id`, `team_id`, `created_at` or `owner_id` as extra
  RPC arguments fails with `PGRST202` (no such signature): **no RPC signature accepts client-supplied identity at
  all**, which is a stronger property than rejecting the values at runtime. The stored `created_at` equals the value
  the RPC returned, exactly.
- **Uniform `not_found` (a3).** A real foreign session id and a random uuid are byte-identical on all seven paths —
  `send_message` (as recipient and as sender), `session_heartbeat`, `close_session`, `fetch_inbox`, `ack_messages`
  and `register_session` resume. Same 73-byte payload each time:
  `{"code":"P0002","details":null,"hint":null,"message":"brigade:not_found"}`.
- **`join_team` (a6).** Unknown team and known-team-wrong-secret both return HTTP 200
  `{"status": "invalid_secret"}`, 28 bytes, byte-identical — at 41 ms each. One real bcrypt on both paths, so timing
  parity holds with no dummy-hash placeholder to break on.
- **`list_members` (a8).** A non-member gets byte-identical `brigade:unauthorized` (76 bytes, SQLSTATE 42501) for a
  real foreign team id and for a random uuid. No team-existence oracle.
- **Revocation (a7).** After `leave_team`, the principal loses direct selects on all four tables *and* `fetch_inbox`
  immediately, in the same request sequence — no lag, no cache window.

## Check (i) — the explicit per-function revokes work

All 14 REST-reachable brigade functions return HTTP 403, SQLSTATE `42501`, message exactly
`permission denied for function <name>` to both service-credential variants (`sb_secret_` key alone, and that key
plus the legacy `service_role` JWT). The request stops at the `EXECUTE` privilege check; the body is never entered.
This is the behaviour the revokes were added for — the pre-revoke stack let the call through and it failed *inside*
with `28000`.

Two additions made during adversarial review:

- `owned_active_session`, an internal helper, is nonetheless addressable at `/rest/v1/rpc/` and is correctly denied.
- Server-only functions (`gc_expired`, `owned_active_session`) are denied to **authenticated members** too, not just
  to service credentials — so the "granted to nobody" intent holds against real users, which is the case that matters.

## Check (d) — pgTAP fixture facts

**The minimal `auth.users` insert is `id` alone** — looser than 9.3's predicted `id, aud, role, is_anonymous,
possibly instance_id`. `id` is the only NOT NULL column without a default. But note what the other columns become:

| Column | After an `id`-only insert |
| --- | --- |
| `aud` | empty string (not `authenticated`) |
| `role` | empty string (not `authenticated`) |
| `is_anonymous` | `false` (column default) |
| `instance_id` | `null` |

So an `id`-only fixture is *sufficient* for `auth.uid()` and the stamping triggers, but the Phase 2 fixture helpers
should still set `aud`, `role` and `is_anonymous` explicitly rather than inherit empty strings, because anything that
later reads those columns will not get what it expects.

The 9.3 `pg_temp.as_user(uid)` pattern was exercised against the stamping triggers and behaves exactly as designed:

- Setting only the two JWT GUCs (`request.jwt.claim.sub`, `request.jwt.claims`), with no `set local role`, gives
  `auth.uid() = uid` while `current_user` stays `postgres`.
- A direct `postgres` insert into `sessions` carrying a **forged** `owner_id` is stored with the uid from the claims,
  not the forged value.
- The same insert with the claims cleared raises `brigade:unauthenticated` from `brigade.stamp_session()`.

Both fixture transactions were rolled back; verified zero leftover rows before and after.

## Check (h) — pg_cron is available on the minimal stack

`pg_cron` 1.6.4 is present on the `-x` stack of 5.9, `create extension if not exists pg_cron` succeeds, and
`cron.schedule` runs. Two jobs are scheduled by the housekeeping migration:

```
17 * * * *   select brigade.gc_expired()
23 3 * * *   delete from cron.job_run_details where end_time < now() - interval '7 days'
```

**This closes the open question** "pg_cron availability on the minimal local stack". The fallback (opportunistic gc
only, with the hosted Cron integration documented as the scheduler) is not needed locally. The housekeeping migration
still guards the scheduling so a stack without pg_cron applies cleanly and degrades to opportunistic gc.

## Two gateway behaviours the adapter must be written against

1. **`P0002` surfaces as HTTP 500.** The `brigade:not_found` raises reach the client as HTTP 500 with SQLSTATE
   `P0002` in the body. The payloads stay byte-identical, so the security property is unaffected, but **adapters must
   key on SQLSTATE, not HTTP status** — a 5xx here is a normal, expected outcome, not a server fault, and retry logic
   that keys on status would retry a permanent error. This is direct evidence for the open question of whether
   `not_found` should move off `P0002` to a `PT4xx` code in P2-2.
2. **Publishable-key-without-JWT denials arrive as HTTP 401**, carrying SQLSTATE `42501` and
   `permission denied for schema brigade` — whereas table-level denials *with* a JWT arrive as HTTP 403 with
   `permission denied for table <name>`. Same SQLSTATE, two different HTTP statuses and two different messages.

## Why this suite is trustworthy

The first draft of the harness passed all its assertions, and an adversarial review pass then found seven places
where a pass proved less than it appeared to. All were strengthened before this result was recorded:

- **The seven `a3` byte-identity tests had no positive controls.** If those RPCs had returned `not_found` for *every*
  id, including owned ones, all seven comparisons would still have passed while proving nothing. Each now proves a
  200 on an owned session first.
- **The four `a7` revocation tests had no pre-revocation baseline** — they would have passed if RLS had been
  over-tight and the principal had never seen rows while active. The suite now asserts it saw rows seconds before.
- **`a2` printed the `created_at` equality in its evidence but only asserted a 5-minute drift bound.** Now asserts equality.
- **The `i-*` checks asserted only the SQLSTATE and a substring**, so a denial naming a different function would have
  passed. Now assert HTTP 403 and the exact message naming the function under test.
- **`a4` accepted any error carrying `42501`** without requiring a permission-denied message.
- **`a1-messages-A` did not pin the row count**, so an extra same-team leak could have hidden.
- **Team and principal distinctness was implicit in the fixture flow.** A uuid collision or a cached signup would
  have silently voided every isolation test; now asserted explicitly.

No migration defects were found in either pass.
