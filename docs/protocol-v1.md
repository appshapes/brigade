# Brigade Adapter Protocol v1 (BAP/1)

**Status.** This document is the Brigade Adapter Protocol, major version 1 ("BAP/1"), and it is **frozen as of the
commit that merges it**. It supersedes section 4 of the implementation plan, which from that commit is history. Changing
any wire shape described here — a member name, an enumerated value, a cap, an error code, an exit status, an NDJSON
event or command — means changing `internal/protocol` (the Go types and their `Validate()` methods),
`docs/protocol-v1.schema.json` (`make schema`), the conformance suite (`internal/conformance`, `brigade-conformance`)
and both bundled adapters (Supabase and fs) **in one commit**. A change that an existing conforming adapter would fail
is a new major version, not an edit to this one.

## How to read this document

- **Normative words.** MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as RFC 2119 defines them. Everything else
  is description.
- **Every MUST cites a conformance case.** The suite (plan section 9.2) has 45 cases: `C-01`..`C-43` plus `C-03b`,
  `C-19b` and `C-29b` (the numbering skips 09). A MUST that no case checks yet is marked `[no case: B-n]` and listed in
  Appendix B, which is an input to the suite's implementation (P1-6). No citation here names a case that does not
  exist; Appendix A is the index.
- **Section numbers are the plan's.** Sections are numbered 4.1–4.10 so that the code comments, the conformance
  suite's rule column (`C-30  FAIL  … 4.5.3 ack idempotent`) and the plan all cross-reference by the same numbers.
- **Authority.** This document is authoritative for the wire. `internal/protocol` implements it: the Go types are the
  reference shapes and each type's hand-written `Validate()` is the normative validity check. The JSON Schema
  (`docs/protocol-v1.schema.json`) is generated from those types and is advisory (see JSON conventions, rule 6).
- **Owner's decisions.** Ten questions the plan's outline left open were settled by the project owner on 2026-09-01.
  Appendix C maps each decision to the sentence that honours it.

## JSON conventions

These rules apply to every document in this specification: the stdin request, the stdout envelope, every `result`
object, every NDJSON event and command.

1. **Documents.** Every document is UTF-8 JSON. Member names are case-sensitive; a wrongly-cased member is an unknown
   member (rule 2), never a match. A document that is not valid UTF-8 is not a document and is rejected as
   `invalid_input` (C-02). The reference codec also rejects a document carrying a duplicate member name; adapters
   SHOULD do the same, since two values for one member cannot both be honoured.
2. **Unknown members are accepted and ignored.** A consumer MUST NOT reject a document because it carries a member the
   consumer does not know (C-17). Unknown members do **not** survive re-serialisation: a consumer that re-emits a
   document emits only the members it knows (C-17, "the fields are not echoed"). Producers never remove or retype a
   member within a major version; additions are announced through `capabilities` (4.7), never inferred from a version
   string (4.5.13).
3. **Required arrays are always present.** A REQUIRED array member is always emitted and is `[]` when empty; omission
   of an empty value applies only to OPTIONAL members (C-18 `capabilities`; C-30 `acked` and `unknown`; C-41
   `message_ids` and `unknown` of the `acked` event). This settles `capabilities`, `acked`, `unknown`, `messages`,
   `sessions`, `members` and `message_ids` at once. A consumer SHOULD nonetheless treat an absent required array as
   empty.
4. **Optional members, null and absence.** An OPTIONAL member is omitted when it has no value. Where a document needs
   to distinguish "no value" from "unchanged" (the members of `HeartbeatRequest` and of the watch `heartbeat`
   command), absence means unchanged. The members that may carry an explicit JSON `null` are the nullable ones in the
   schema: `session_description`, `workspace_label`, `lease_seconds`, `resume`, `reply_to` in a `MessageEnvelope` (not in a
   `SendRequest`), and the optional members of `HeartbeatRequest` and `WatchCommand`. `retryable` is never `null` (4.3).
5. **Two kinds of cap.** A cap named `*_bytes` is measured in bytes of UTF-8 (`len`); a cap named `*_chars` or
   `*_codepoints` is measured in Unicode code points (`utf8.RuneCountInString`). A 16 KiB body is not 16,384
   characters. A validation failure names the unit in `details.unit` (4.3.1).
6. **The schema is advisory; `Validate()` is normative.** `docs/protocol-v1.schema.json` (JSON Schema draft 2020-12,
   generated by `cmd/brigade-schema`, drift-checked by `make schema-check`) carries a `required` array per type
   listing the members a conforming producer always emits — every member without `omitzero`, the same rule as
   convention 3 — which includes every member `Validate()` requires unconditionally. Members that are required only
   conditionally (`result`/`error` by `ok`, the `profile` team members by `state`, the `ack` command's
   `message_ids` by `type`) and everything the schema cannot express (the byte cap on `body`, the 4.4.6 rejection rule
   in full, `lease.default_seconds` within `min..max`) are checked by `Validate()` alone. Where the schema and
   `Validate()` disagree, `Validate()` is right and the schema is regenerated.
7. **Timestamps** are RFC 3339 strings (Go `time.Time`, `2026-08-30T12:00:00Z`). Every timestamp in every example
   below is a real value; an ellipsis `…` appears only inside opaque identifier strings, never in a typed member, so
   every example parses and validates as written. Every example of a shape that has a Go type is, byte for byte, a
   file under `internal/protocol/testdata/examples/`, which the schema tests validate and round-trip; the four
   composite results that have no Go type (`session register`, `session list`, `message receive`, `team members`)
   are checked member by member. `TestSpecExamplesAreTheTestdataFiles` in `internal/protocol/schema` pins both
   directions, so neither this document nor a file can change alone.
8. **Identifiers are opaque.** `principal_ref`, `session_id`, `team_ref` and `message_id` are non-empty strings with no
   structure a consumer may rely on (4.8). `session_name`, `human_label` and `team_name` are unverified display
   strings and are untrusted input at every layer (4.5.11).

## 4.1 Invocation model

**Process model.** The harness executes the adapter as an argument array, never through a shell:
`exec.Command(os.Executable(), "adapter", "supabase", …)` for the bundled adapter and
`exec.Command(command, fixedArgs…, args…)` for a third-party adapter configured as an absolute path or as a JSON array
`["<command>", "<fixed arg>", …]` (D26). Third-party adapters are real executables (a script needs a shebang line);
there is no shell form and no Windows form (D33).

**Grammar.** `<group> <verb> [flags]`. The groups are `describe` (which takes no verb), `team`, `session`, `message`
and `profile`. `describe`, `session *` and `message *` are the **frozen core**; `team *` and `profile *` are
**conventions** (4.2). On a core command the flags are exactly:

| Flag | Applies to | Default |
| --- | --- | --- |
| `--profile <name>` | every command | `BRIGADE_PROFILE`, else `default` |
| `--session <id>` | the session and message verbs that act on one session | required where listed in 4.2 |
| `--include-offline` | `session list` | off |
| `--limit <n>` | `message receive` | 50 (maximum 200) |
| `--log-level error\|warn\|info\|debug` | every command | `BRIGADE_LOG_LEVEL` |

An unknown flag on a core command MUST be refused with `usage` (C-02). `team *` and `profile *` MAY define additional
flags, provided no flag ever carries a secret, a message body or a user-authored message; display names and labels MAY
be flags on those conventions because they are neither secret nor message content. `--join-secret <value>` MUST be
refused with `usage` on every adapter (C-05). The convention flags are `team create [--name <team_name>] [--label
<human_label>] [--prompt] [--secret-file <path>]` and `team join [--prompt] [--label <human_label>]` (4.4.10;
`--prompt` asks on a TTY, the secret without echo); the Supabase adapter's extras (`profile init --url <https-url>
--key <publishable-key> [--force]`) are that adapter's own.

**stdin.** One UTF-8 JSON document terminated by EOF (a trailing newline is allowed), at most 1 MiB; a longer stdin
MUST be refused with `invalid_input` (C-02), an empty stdin on a command that takes input is `invalid_input`, and a
malformed document is `invalid_input` (C-02). A command that takes no input MUST NOT read stdin at all — the harness
spawns such commands with stdin ignored (the null device), and a read would block forever when a human runs the
adapter by hand (C-01). For `message watch`, stdin is a stream of NDJSON commands (4.4.9) when the adapter
advertises `message.watch.stdin_commands`; otherwise the adapter ignores stdin's content and exits on its EOF.

**stdout.** Exactly one JSON document — a 4.3 envelope — for every command except `message watch`, which writes
NDJSON events (4.4.9). Nothing else is ever written to stdout, including at `--log-level debug` (C-01, C-02, C-33; the
suite runs every adapter at `BRIGADE_LOG_LEVEL=debug`, so every case is also this check).

**stderr.** Free-form diagnostics. NDJSON is recommended (`{"ts","level","comp","event",…}`) with the redaction filter
applied; no secret appears on stderr at any log level (C-05). The harness captures stderr for its own log at debug
level and never shows it to the model.

**Environment.** The adapter reads `BRIGADE_PROFILE`, `BRIGADE_CONFIG_DIR`, `BRIGADE_STATE_DIR`, `BRIGADE_LOG_LEVEL`,
`HOME` and the XDG variables. It MUST NOT require any other variable (C-01). Under a live Claude Code session the
harness builds the child's environment **from scratch** — it passes only `PATH`, `HOME`, `TMPDIR`, `XDG_*`, `LANG`,
`LC_*`, `CLAUDE_CONFIG_DIR`, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and their lowercase forms),
`SSL_CERT_FILE` and `SSL_CERT_DIR` when non-empty, plus the harness-computed `BRIGADE_PROFILE`, `BRIGADE_CONFIG_DIR`,
`BRIGADE_STATE_DIR` and `BRIGADE_LOG_LEVEL` (plan 3.2; `GODEBUG`, `GOFLAGS`, `NODE_OPTIONS`, `CLAUDE_CODE_MESSAGING_*`
and every other inherited variable are absent by construction). **Adapter-specific `BRIGADE_<ADAPTER>_*` variables
therefore never arrive under a live session.** An adapter's own configuration (backend URL, keys, a storage root)
comes from its profile file (written by `profile init` or by `team join`'s `backend` member, 4.4.10) or from fixed
arguments in the `adapter_command` JSON array; a `BRIGADE_<ADAPTER>_*` variable is honoured only when a human runs the
adapter from their own shell. The conformance suite passes an equally minimal environment, so an adapter that needs
anything else fails C-01 with a clear message.

**Timeouts.** The harness applies 20 s to every request/response command (registration 8 s at `SessionStart`, close
1 s at `SessionEnd`, 3 s from the watcher). `message watch` runs until stdin EOF, a `close` command, SIGTERM or a fatal
error (4.4.9).

**Exit.** A command returns its exit status (4.6) to the dispatcher, which flushes stdout before the process exits, so
a result is never truncated by an early exit.

## 4.2 Command surface

Only `describe`, `session *` and `message *` are the frozen core. `team *` and `profile *` are conventions: named here
so that every adapter uses the same words, gated by capability, and permitted extra flags under the rule of 4.1.

| Command | stdin | stdout `result` | Required |
| --- | --- | --- | --- |
| `describe` | none | `DescribeResult` (4.4.1) | **core.** MUST work offline, without credentials, and MUST NOT create a principal or touch the network (C-01, C-07) |
| `session register` | `SessionRegistration` (4.4.2) | `SessionRecord` (4.4.3) plus `resumed`, `lease_seconds`, `server_time` | **core.** `conflict` with `details.reason = "session_live"` when `resume.session_id` names a session that is open with a valid lease (4.5.8, C-19b) |
| `session heartbeat --session <id>` | `HeartbeatRequest` (4.4.4) | `{session_id, state, lease_until, server_time}` | **core** (C-13) |
| `session list [--session <id>] [--include-offline]` | none | `{team_ref, team_name, server_time, sessions: SessionRecord[], truncated}` | **core.** Only the profile's team; offline sessions omitted without the flag; `is_self` set when `--session` is given (C-12) |
| `session close --session <id>` | none | `{session_id, state: "offline"}` | **core.** Idempotent (C-15) |
| `message send` | `SendRequest` (4.4.6) | `SendResponse` (4.4.7) | **core** (C-20) |
| `message receive --session <id> [--limit <n>]` | none | `{messages: MessageEnvelope[]}` | **core.** One-shot, oldest first (SHOULD, 4.5.10), default 50, maximum 200; never acknowledges (C-20, C-30) |
| `message watch --session <id>` | NDJSON commands (capability `message.watch.stdin_commands`) or nothing | NDJSON events (4.4.9) | **core** (C-33..C-41) |
| `message ack --session <id>` | `{message_ids: string[]}` | `{acked: string[], unknown: string[]}` | **core.** Idempotent (C-30) |
| `team create [--name <team_name>] [--label <human_label>] [--prompt] [--secret-file <path>]` | `{team_name, human_label?}` (or the flags, or a TTY prompt with `--prompt`) | `{team_ref, team_name, join_secret, principal_ref}` | convention, capability `team.create`; the only command that prints a secret, once; exit 7 `conflict` with `details.reason = "profile_bound"` on a profile already bound to a team (4.4.10, C-03, C-03b) |
| `team join [--prompt] [--label <human_label>]` | `{join_secret, human_label?, backend?}` (or a TTY prompt with `--prompt`: the secret without echo, then the label) | `{team_ref, team_name, principal_ref, rejoined}` | convention, capability `team.join` (an adapter whose membership is managed elsewhere omits it); binds the profile; `backend` is adapter-specific and accepted only when the profile has no backend configured; exit 7 `conflict` (`profile_bound`) on a profile bound to another team — a secret naming the bound team is a rejoin (4.4.10, C-04, C-08) |
| `team leave` | none | `{team_ref, principal_ref, left: true}` | convention, capability `team.join`; idempotent; revokes the caller's own membership at the backend, closes the caller's open sessions in that team and unbinds the profile (`describe.profile.state` becomes `not_member`, the credential stays); a later `team join` with the secret re-activates the same membership (`rejoined: true`) and keeps the principal (C-08) |
| `team members` | none | `{team_ref, team_name, server_time, members: [{principal_ref, human_label, status, joined_at, last_seen_at, session_count}]}` | convention, capability `team.roster` (D22); every active member; `unauthorized` with byte-identical text for a non-member's team and a random `team_ref` (C-43) |
| `team rotate-secret` / `team revoke-member` / `team transfer` | adapter-defined | adapter-defined | convention, capability `team.admin`, Phase 5; creator only; not specified further in v1 |
| `profile init` / `profile status` / `profile reset` / `profile revoke-credentials` | adapter-specific | adapter-specific, never a secret | convention, adapter-defined; `profile reset` invalidates the credential at the backend when the adapter can (best effort) and deletes the local credential and profile; `profile revoke-credentials` only invalidates the credential (so a leaked copy of the credential file stops working) and leaves the profile in place for a rejoin; `profile init` on a configured profile is `conflict` unless the adapter's own `--force` is given |

Result objects that have a Go type in `internal/protocol` are named in the table; the composite results of
`session register`, `session list`, `message receive` and `team members` are described member by member in 4.4.

## 4.3 Result envelope

Every command except `message watch` writes exactly one envelope:

```json
{"ok": true, "protocol_version": "1", "result": {"session_id": "…", "state": "offline"}}
```

```json
{"ok": false, "protocol_version": "1", "error": {"code": "rate_limited", "message": "…", "retryable": true, "retry_after_ms": 12000, "details": {"reason": "recipient_inbox_full"}}}
```

| Member | Type | Presence | Meaning |
| --- | --- | --- | --- |
| `ok` | boolean | required | `true` with `result`, `false` with `error`; never both, never neither |
| `protocol_version` | string | required | the protocol major, `"1"` (4.5.13) |
| `result` | object | exactly when `ok` is `true` | the command's result (4.2, 4.4) |
| `error` | object | exactly when `ok` is `false` | the error object below |
| `error.code` | string | required | one of the twelve codes of 4.6 |
| `error.message` | string | required | short, human-readable, safe to show to a model: no raw server text, no SQL, no tokens, no interpolated input value |
| `error.retryable` | boolean | required (see below) | whether a retry of the same command can succeed |
| `error.retry_after_ms` | integer ≥ 0 | present for `rate_limited` | how long to wait before retrying |
| `error.details` | object of strings | optional | machine-readable detail (4.3.1) |

On `ok: false` the process exit status MUST match the code's row in 4.6 (C-02, C-06; every failing case asserts both
halves).

**`retryable`.** An adapter MUST send `retryable` on every failing envelope and on every watch `error` event
(C-02, C-37). A consumer that receives an error object without it treats it as `false`: absent fails safe. Consumers
SHOULD derive retryability from `code` rather than from the flag — only `rate_limited` (exit 8) and `unavailable`
(exit 9) are ever retryable, so the flag is advisory and can never make another code retryable. The member is a plain
boolean, never `null`.

### 4.3.1 Validation failure details

When a command fails with `invalid_input` because a member of the stdin document is missing, malformed, out of range
or over its cap, `details` carries the following members, with these frozen meanings:

| Key | Value |
| --- | --- |
| `field` | the offending member's **wire name**: its JSON name, dotted for nesting, e.g. `session_name`, `resume.session_id`, `sender.principal_ref`, `limits.max_body_bytes`; `stdin` when stdin itself is the problem (empty, or over 1 MiB) |
| `reason` | a short machine-readable token naming the rule that failed |
| `limit` | the cap or bound that was exceeded, as a decimal string |
| `actual` | the offending value's measured size, as a decimal string |
| `unit` | `bytes` or `codepoints` — which of the two caps of JSON convention 5 was applied |

`field` is present on every validation failure of a named member; `reason` accompanies it; `limit`, `actual` and
`unit` accompany a cap violation. A stdin document that does not parse as JSON at all carries `reason =
"malformed_json"` and no `field`, because no member can be named. `details` is otherwise adapter-specific (4.3), so other keys MAY appear (the
reference implementation adds `allowed` for an enumeration failure and `min`/`max` for a range failure, and uses the
`reason` tokens `required`, `too_long`, `invalid_value`, `not_utf8`, `forbidden_member`, `out_of_range` and
`malformed_json`, plus `read_error` and — on the `usage` refusal of a terminal stdin (4.6) — `terminal` from its stdin
reader; those tokens and extra keys are informative, not frozen). The offending value itself is never echoed
into `message` or `details`: member names and values in a hostile document are attacker-controlled (C-16, C-27 assert
the code and `field`, never the text).

The other `details.reason` values this specification fixes are listed with their codes in 4.6.

## 4.4 JSON shapes

Each shape below names its Go type in `internal/protocol`. "Required" and "optional" are as `Validate()` enforces
them; the schema's `required` arrays are generated from the same list (JSON convention 6).

### 4.4.1 `DescribeResult`

Answered from local state only.

```json
{
  "protocol_version": "1",
  "adapter": {"name": "brigade-adapter-supabase", "version": "0.1.0"},
  "delivery": {"guarantee": "at_least_once", "ordering": "none", "ack_state": "injected"},
  "capabilities": ["team.create", "team.join", "team.roster", "message.receive", "message.watch.push", "message.watch.stdin_commands",
                   "session.description", "session.resume", "session.workspace_label", "session.inbound"],
  "limits": {"max_body_bytes": 16384, "max_summary_chars": 200, "max_session_name_codepoints": 64,
             "max_team_name_codepoints": 64, "max_description_chars": 256, "max_human_label_chars": 128,
             "max_workspace_label_chars": 128, "max_idempotency_key_chars": 128,
             "send_rate": {"per_minute": 20, "per_hour": 200}, "principal_send_rate": {"per_minute": 60, "per_hour": 600},
             "max_unacked_per_recipient": 60, "max_unacked_per_sender_recipient": 15,
             "max_hop_count": 32, "implicit_reply_window_seconds": 600},
  "lease": {"default_seconds": 90, "min_seconds": 30, "max_seconds": 600},
  "retention": {"unacked_message_seconds": 604800, "acked_message_seconds": 86400, "closed_session_seconds": 604800},
  "profile": {"name": "default", "state": "joined", "team_ref": "…", "team_name": "ops", "principal_ref": "…", "human_label": "alice@example.com"}
}
```

| Member | Required | Notes |
| --- | --- | --- |
| `protocol_version` | yes | the adapter's protocol major (4.5.13) |
| `adapter.name`, `adapter.version` | yes | free strings identifying the adapter build |
| `delivery.guarantee` | yes | `at_least_once` is the only v1 value |
| `delivery.ordering` | yes | a free string; the bundled adapters answer `none` (4.5.10) |
| `delivery.ack_state` | yes | `injected` (the terminal adapter state in v1) or `processed` (reserved, 4.5.3) |
| `capabilities` | yes | strings from the registry of 4.7; always present, `[]` when empty (JSON convention 3); MUST include `message.receive` in v1 (C-18) |
| `limits`, `lease`, `retention` | yes | every member below present with a positive number (C-18); `lease.min_seconds ≤ lease.default_seconds ≤ lease.max_seconds` |
| `profile.name` | yes | the profile the command ran against |
| `profile.state` | yes | see below |
| `profile.team_ref`, `profile.team_name`, `profile.principal_ref`, `profile.human_label` | only when `state` is `joined` | absent in every other state (C-01, C-07) |

**`profile.state`** is `unconfigured` (no profile file), `unauthenticated` (a profile exists but no usable credential
file), `not_member` (credential present, no team bound) or `joined`. It is computed from local files only, so
`describe` never fails and never makes a network call (C-01, C-07).

**`limits`.** The values above are the protocol's v1 constants and are the caps every adapter enforces on input:
the conformance suite asserts that a value exactly at each cap is accepted (C-16, C-27), so an adapter may not
advertise or enforce a tighter one. Each cap governs the following members, in the stated unit:

| `limits` member | Unit | Governs |
| --- | --- | --- |
| `max_body_bytes` | bytes | `body` (4.4.5, 4.4.6) |
| `max_summary_chars` | code points | `summary` (4.4.5, 4.4.6) |
| `max_session_name_codepoints` | code points | `session_name` everywhere: 4.4.2, 4.4.3, 4.4.4, `sender.session_name` (4.4.5), the watch `heartbeat` command (4.4.9) |
| `max_team_name_codepoints` | code points | `team_name` everywhere: `team create` request and result, `team join` result (4.4.10), `describe.profile.team_name`, `session list` and `team members` results |
| `max_description_chars` | code points | `session_description` (4.4.2, 4.4.3, 4.4.4) |
| `max_human_label_chars` | code points | `human_label` everywhere: 4.4.3, `sender.human_label` (4.4.5), `team create` and `team join` requests (4.4.10), `describe.profile.human_label`, `team members` |
| `max_workspace_label_chars` | code points | `workspace_label` (4.4.2, 4.4.3) |
| `max_idempotency_key_chars` | code points | `idempotency_key` (4.4.6) |
| `send_rate.per_minute`, `send_rate.per_hour` | messages | one sender session's send budget (4.5.12) |
| `principal_send_rate.per_minute`, `principal_send_rate.per_hour` | messages | one principal's send budget summed over all its sessions (4.5.12) |
| `max_unacked_per_recipient` | messages | unacknowledged messages one recipient session may hold (4.5.12) |
| `max_unacked_per_sender_recipient` | messages | unacknowledged messages from one sender session to one recipient session (4.5.12) |
| `max_hop_count` | hops | the `hop_count` beyond which a send is `loop_detected` (4.5.12) |
| `implicit_reply_window_seconds` | seconds | the window in which an unlabelled answer counts as a reply (4.5.12) |

A team name is 64 code points because it is printed as a frame tag attribute, and the sanitiser caps attribute values
at 64 code points (plan 6.7 rule 4); a workspace label is 128 because it is a label, like `human_label`. Both are
published in `describe` so programs read the number rather than this prose.

**`lease`** is the range of `lease_seconds` an adapter accepts (4.5.8); **`retention`** is the set of floors of 4.5.9.

### 4.4.2 `SessionRegistration` (harness → adapter)

```json
{
  "harness": "claude-code", "harness_version": "2.1.251",
  "session_name": "payments-api", "session_description": null,
  "activity": "busy", "inbound": "accept", "lease_seconds": 90, "workspace_label": null,
  "resume": {"session_id": "a Brigade session_id previously returned to this principal"}
}
```

| Member | Required | Notes |
| --- | --- | --- |
| `harness`, `harness_version` | yes | identify the registering harness |
| `session_name` | yes | ≤ `max_session_name_codepoints` (C-16) |
| `session_description` | optional, nullable | ≤ `max_description_chars` (C-16); capability `session.description` |
| `activity` | yes | `busy` or `idle` |
| `inbound` | yes | `accept`, `hold` or `refuse` — the harness's inbound policy, so senders can see it; adapters without `session.inbound` ignore it (C-42) |
| `lease_seconds` | optional, nullable | within `lease.min_seconds..lease.max_seconds`, else `invalid_input`; absent means `lease.default_seconds` |
| `workspace_label` | optional, nullable | ≤ `max_workspace_label_chars`; opt-in and user-typed; capability `session.workspace_label` |
| `resume.session_id` | optional | capability `session.resume`; see below |

The registration has no member for a native session id, a working directory, a hostname, a username or a transcript
path (threat model T10, unit test U-22); adding one is a protocol change, not a convenience.

**Resume.** An adapter MUST NOT let a caller re-open a session it does not own — the answer is the uniform `not_found`
(C-19) — and MUST NOT re-open a session that is open with a valid lease (`conflict`, `details.reason =
"session_live"`, 4.5.8, C-19b). A re-opened session keeps its id and its pending messages (C-19).

**Result** of `session register`: the `SessionRecord` of 4.4.3 with three more members — `resumed` (boolean, `true`
when `resume.session_id` was honoured, C-10, C-19), `lease_seconds` (integer, the lease actually granted) and
`server_time` (timestamp, the adapter's clock):

```json
{
  "session_id": "…", "session_name": "payments-api", "session_description": null,
  "principal_ref": "…", "human_label": "alice@example.com",
  "state": "active", "activity": "busy", "inbound": "accept",
  "last_seen_at": "2026-08-30T12:00:00Z", "lease_until": "2026-08-30T12:01:30Z",
  "harness": "claude-code", "harness_version": "2.1.251", "workspace_label": null,
  "created_at": "2026-08-30T11:55:00Z", "is_self": false,
  "resumed": false, "lease_seconds": 90, "server_time": "2026-08-30T12:00:00Z"
}
```

```json
      "created_at": "2026-08-30T11:55:00Z", "is_self": true
    }
  ],
  "truncated": false
}
```

**Result** of `session close`: `{"session_id": "…", "state": "offline"}` (the `result` of the first envelope in 4.3;
C-15).

### 4.4.4 `HeartbeatRequest` and `HeartbeatResult`

```json
{"activity": "idle", "session_name": "payments-api", "session_description": "tenant_id migration runner", "inbound": "hold", "lease_seconds": 120}
```

Every member is optional and absent means unchanged (JSON convention 4); the session comes from `--session`. When
present: `activity` is `busy` or `idle`; `session_name` is non-empty and ≤ `max_session_name_codepoints`;
`session_description` ≤ `max_description_chars`; `inbound` is `accept`, `hold` or `refuse`; `lease_seconds` within
`lease.min_seconds..lease.max_seconds`. A heartbeat renews `lease_until` and applies the new values (C-13, C-42).

```json
{"session_id": "…", "state": "idle", "lease_until": "2026-08-30T12:03:00Z", "server_time": "2026-08-30T12:01:00Z"}
```

All four result members are required; `state` is `active`, `idle` or `offline`.

### 4.4.5 `MessageEnvelope` (adapter → harness)

The only representation of a message anywhere in the protocol.

```json
{
  "protocol_version": "1", "kind": "text", "message_id": "…", "team_ref": "…",
  "sender": {"principal_ref": "…", "human_label": "alice@example.com", "session_id": "…", "session_name": "payments-api"},
  "recipient_session_id": "…", "summary": "Migration completed", "body": "The tenant_id migration has landed.",
  "reply_to": null, "hop_count": 0, "created_at": "2026-08-30T12:00:00Z", "delivery_state": "accepted"
}
```

| Member | Required | Notes |
| --- | --- | --- |
| `protocol_version` | yes | `"1"` |
| `kind` | yes | `text` is the only v1 value (4.5.11) |
| `message_id`, `team_ref` | yes | opaque; adapter-stamped |
| `sender.principal_ref`, `sender.session_id`, `sender.session_name` | yes | adapter-stamped from its own authority (4.5.5, C-20); `session_name` ≤ `max_session_name_codepoints` |
| `sender.human_label` | optional | adapter-stamped; ≤ `max_human_label_chars`; unverified |
| `recipient_session_id` | yes | opaque |
| `summary` | optional | ≤ `max_summary_chars`; sender-supplied, untrusted |
| `body` | yes | non-empty UTF-8, ≤ `max_body_bytes` **bytes**; untrusted |
| `reply_to` | optional, nullable | the `message_id` this message answers; when present it is non-empty |
| `hop_count` | yes | integer in `0..max_hop_count`, adapter-computed (4.5.12) |
| `created_at` | yes | adapter-stamped timestamp |
| `delivery_state` | yes | `accepted` (persisted, 4.5.1), `injected` (the terminal adapter state in v1) or `processed` (reserved) |

**Result** of `message receive`: `{"messages": MessageEnvelope[]}`; `messages` is always present, `[]` when the inbox
is empty (JSON convention 3, C-30):

```json
{"messages": [
  {
    "protocol_version": "1", "kind": "text", "message_id": "…", "team_ref": "…",
    "sender": {"principal_ref": "…", "human_label": "alice@example.com", "session_id": "…", "session_name": "payments-api"},
    "recipient_session_id": "…", "summary": "Migration completed", "body": "The tenant_id migration has landed.",

  }
]}
```

### 4.4.6 `SendRequest` (harness → adapter)

```json
{"sender_session_id": "…", "recipient_session_id": "…", "body": "…", "summary": "optional", "reply_to": "optional message_id", "idempotency_key": "≤128 chars"}
```

| Member | Required | Notes |
| --- | --- | --- |
| `sender_session_id` | yes | MUST be a session owned by the profile's principal, otherwise `not_found` (C-24) |
| `recipient_session_id` | yes | a session of the profile's team, otherwise `not_found` (C-25) |
| `body` | yes | non-empty, ≤ `max_body_bytes` bytes (C-27) |
| `summary` | optional | ≤ `max_summary_chars` (C-27) |
| `reply_to` | optional | a `message_id` the sender session received, otherwise `not_found` (C-29) |
| `idempotency_key` | optional | ≤ `max_idempotency_key_chars` (4.5.4) |

This is the one shape where loose parsing has a named exception. A request carrying a `sender` member, or a
`principal_ref`, `human_label`, `team_ref`, `created_at` or `hop_count` member — with any value, `null` included —
MUST be rejected with `invalid_input`, `details.field` naming the member, before any network call (C-23): silently
ignoring a forged sender field would hide a client bug. The reference implementation reports
`details.reason = "forbidden_member"`; reason tokens are informative (4.3.1).

### 4.4.7 `SendResponse`

```json
{"status": "accepted", "message_id": "…", "recipient_session_id": "…", "created_at": "2026-08-30T12:00:05Z", "duplicate": false, "hop_count": 0}
```

All six members are required. `status` is `accepted` — the only value; the product never says "delivered" (4.5.1).
`duplicate: true` means the idempotency key matched an existing message and `message_id` is that message's id (4.5.4,
C-21). `hop_count` is the value the adapter computed for this message (4.5.12, C-29).

### 4.4.8 `message ack`

Request `{"message_ids": ["…"]}` (the session comes from `--session`); `message_ids` is required, non-empty, and every
element is a non-empty string.

```json
{"message_ids": ["…"]}
```

Result `{"acked": [...], "unknown": [...]}`; both arrays are always present, `[]` when empty (JSON convention 3).

```json
{"acked": ["…"], "unknown": []}
```

An already-acknowledged owned id counts as `acked`; an id that is not owned by the session or not found is `unknown`,
never an error (C-30).

### 4.4.9 `message watch`: events and commands

stdout is NDJSON: one JSON object per line, `\n`-terminated, no blank lines and no other stdout output (C-33). Each
event carries an `event` discriminator.

```json
{"event": "ready", "protocol_version": "1", "session_id": "…", "mode": "push"}
```

```json
{"event": "message", "message": {
  "protocol_version": "1", "kind": "text", "message_id": "…", "team_ref": "…",
  "sender": {"principal_ref": "…", "human_label": "alice@example.com", "session_id": "…", "session_name": "payments-api"},
  "recipient_session_id": "…", "summary": "Migration completed", "body": "The tenant_id migration has landed.",
  "reply_to": null, "hop_count": 0, "created_at": "2026-08-30T12:00:00Z", "delivery_state": "accepted"
}}
```

```json
{"event": "status", "state": "live", "detail": "SUBSCRIBED"}
```

```json
{"event": "status", "state": "polling", "detail": "RealtimeDisabledForTenant"}
```

```json
{"event": "acked", "message_ids": ["…"], "unknown": []}
```

```json
{"event": "heartbeat_ok", "session_id": "…", "state": "active", "lease_until": "2026-08-30T12:01:30Z", "server_time": "2026-08-30T12:00:00Z"}
```

```json
{"event": "error", "error": {"code": "unauthenticated", "message": "…", "retryable": false}}
```

| Event | Members | Meaning |
| --- | --- | --- |
| `ready` | `protocol_version`, `session_id`, `mode` (all required) | emitted exactly once, first, when the initial catch-up starts (C-33). `mode` is `push` or `polling`: an adapter that advertises `message.watch.push` sends `push`; an adapter that omits that capability MUST send `polling` (C-33) |
| `message` | `message` (a `MessageEnvelope`) | one accepted, unacknowledged message; the same `message_id` MAY appear more than once (4.5.2) |
| `status` | `state` (required), `detail` (optional free text) | informational transport state. `state` is `live` (events are arriving by push) or `polling` (the adapter fell back to polling); a receiver MUST ignore a state it does not know `[no case: B-4]` |
| `acked` | `message_ids`, `unknown` (both always present, `[]` when empty) | the answer to a stdin `ack` command (C-41) |
| `heartbeat_ok` | `session_id`, `state`, `lease_until`, `server_time` (all required; `state` is `active`, `idle` or `offline`) | the answer to a stdin `heartbeat` command (C-41) |
| `error` | `error` (the 4.3 error object, `retryable` included) | a failure; an `error` with `retryable: false` is followed by process exit with the matching 4.6 status (C-37) |

**Commands on stdin** (only with `message.watch.stdin_commands`; each is one NDJSON line with a `type`
discriminator):

```json
{"type": "ack", "message_ids": ["…"]}
```

```json
{"type": "heartbeat", "activity": "busy", "session_name": "payments-api", "inbound": "accept", "lease_seconds": 90}
```

```json
{"type": "close"}
```

`ack` (`message_ids` required, non-empty) → an `acked` event; `heartbeat` (`activity`, `session_name`, `inbound`,
`lease_seconds`, each optional with the 4.4.4 rules; there is no `session_description` on this command) → a
`heartbeat_ok` event; `close` → the session is closed as by `session close`, then the process exits 0 (C-41).

**Rules.**

- `ready` MUST be emitted exactly once, before any other event, when the initial catch-up starts (C-33).
- `message` MUST be emitted at least once for every message that is accepted and unacknowledged at any moment while
  the watch runs, including messages accepted before it started (C-34, C-36, C-40). The same `message_id` MAY be
  emitted more than once; an adapter SHOULD re-emit an unacknowledged id at most once per periodic drain (C-36).
- A message accepted while the watch runs is emitted within 5 s when the adapter advertises `message.watch.push`, and
  within two poll intervals otherwise (C-35).
- An `error` event with `retryable: false` MUST be followed by process exit with the matching 4.6 status (C-37,
  within 10 s); an `error` with `retryable: true` is informational and the watch continues.
- `status` is informational; a receiver never acts on it beyond logging.
- Unknown event kinds `[no case: B-5]` and unknown command types (C-41) MUST be ignored by their receiver — logged,
  never fatal. Unknown members inside a known event or command are ignored as everywhere (JSON convention 2).
- A line longer than 1 MiB is dropped by the reader with a warning and reading continues with the next line
  (C-41).
- The watch MUST exit 0 within 5 s of stdin EOF, of a `close` command, or of SIGTERM (C-38, C-41).
- Each event is exactly one physical line: bodies are JSON-encoded, so a body containing `\n`, `\r`, U+2028 or
  U+2029, or text that looks like a JSON auth line, cannot produce a second line and parses back to the same body
  (C-39).

### 4.4.10 Team commands

**`team create`** — request `{"team_name", "human_label"?}` on stdin, or `--name`/`--label`, or `--prompt` (asks for
the name and the label on a TTY; without a TTY `--prompt` is `usage` (C-03, C-04)):

```json
{"team_name": "ops", "human_label": "alice@example.com"}
```

`team_name` is required and ≤ `max_team_name_codepoints`; `human_label` is optional and ≤ `max_human_label_chars`.
Result (C-03):

```json
{"team_ref": "…", "team_name": "ops", "join_secret": "brg1.EXAMPLE-TEAM-REF.EXAMPLE-NOT-A-REAL-SECRET", "principal_ref": "…"}
```

All four members are required. This is the only command output in the protocol that carries a secret; stderr warns
that it is shown once, and with `--secret-file <path>` the secret is written to that path with mode 0600 and omitted
from stdout.

**`team join`** — request `{"join_secret", "human_label"?, "backend"?}` on stdin, or `--prompt` (asks for the secret
without echo, then for the label, echoed and optional, unless `--label` was given):

```json
{"join_secret": "brg1.EXAMPLE-TEAM-REF.EXAMPLE-NOT-A-REAL-SECRET", "human_label": "alice@example.com"}
```

`join_secret` is required; `human_label` is optional and ≤ `max_human_label_chars`; `backend` is optional, MUST be a
JSON object when present (C-02 covers the malformed-document half; the object rule is C-04), is
adapter-specific (Supabase: `{"url", "publishable_key"}`) and is accepted only when the profile has no backend
configured. Result (C-04, C-08):

```json
{"team_ref": "…", "team_name": "ops", "principal_ref": "…", "rejoined": false}
```

All four members are required. `rejoined: true` means the secret named the team the profile was already bound to and
the same membership was re-activated with the same `principal_ref` (C-08).

**Join secret format.** A join secret is `brg1.<team_ref>.<secret>`: the fixed, case-sensitive prefix `brg1.`, the
team's `team_ref`, a `.`, and the secret proper. Because the protocol does not freeze the shape of `team_ref` (4.8),
the `team_ref` is everything between the prefix and the **last** `.`; neither component may be empty or contain
whitespace, control or format characters. A malformed secret is `invalid_input` with `details.field = "join_secret"`
and a message that never contains any part of the input (C-03 parses the created secret with the protocol helper;
C-05 for the no-leak rule).

**Binding rules.** `team create` and `team join` on a profile already bound to a team MUST exit 7 `conflict` with
`details.reason = "profile_bound"` (C-03b, C-04) — use `team leave`, `profile reset` or another `--profile` — with one
exception: a `team join` whose secret names the bound team (the `team_ref` inside the secret equals the profile's) is
a **rejoin** (after `profile revoke-credentials` or an administrator's revocation) and proceeds (C-08). The check is
local, before any network call. A rejected secret is `unauthorized` with text byte-identical for a wrong secret, an
unknown team and a banned principal (C-04, 4.5.7).

**`team leave`** takes no input. Result (C-08):

```json
{"team_ref": "…", "principal_ref": "…", "left": true}
```

`left` is always `true` — the command is idempotent and success is its only non-error outcome (C-08).

**`team members`** takes no input. Result (C-43): `team_ref`, `team_name`, `server_time` and `members`, always present
(`[]` when empty); each member carries `principal_ref`, `human_label` (unverified), `status` (the adapter's membership
status string; the roster lists active members only), `joined_at`, `last_seen_at` (`null` for a member that has never
registered a session) and `session_count`.

```json
{
  "team_ref": "…", "team_name": "ops", "server_time": "2026-08-30T12:00:00Z",
  "members": [
    {"principal_ref": "…", "human_label": "alice@example.com", "status": "active", "joined_at": "2026-08-30T11:50:00Z", "last_seen_at": "2026-08-30T12:00:00Z", "session_count": 1},
    {"principal_ref": "…", "human_label": "bob@example.com", "status": "active", "joined_at": "2026-08-30T11:52:00Z", "last_seen_at": null, "session_count": 0}
  ]
}
```

**`profile init`** on a configured profile is `conflict` unless the adapter's own `--force` is given.

## 4.5 Semantics

1. **Durable acceptance.** `message send` MUST return `ok: true` only after the message is persisted such that a
   subsequent `message receive` for the recipient returns it, absent retention expiry (C-20). Persistence MUST precede
   any push notification (C-36: a message whose `message` event was seen is still there after the watch is killed
   and restarted). The product never says "delivered".
2. **At least once.** `message watch` and `message receive` MUST return every accepted, unacknowledged message (C-34,
   C-36, C-40); duplicates are permitted. The harness deduplicates by `message_id` and tolerates a redelivery after a
   crash between injection and acknowledgement.
3. **Acknowledgement point.** The harness calls `message ack` only after local injection succeeded (4.9). `injected` is
   the terminal adapter state in v1; `processed` is reserved. A message the harness holds or refuses is not
   acknowledged. `message ack` MUST be idempotent: an already-acknowledged owned id is `acked` again, and an id that is
   not owned or not found is `unknown`, never an error (C-30). After acknowledgement the message MUST NOT be returned
   by `message receive` or re-emitted by `message watch` (C-30, C-36).
4. **Idempotency.** Two `message send` calls from the same `sender_session_id` with the same `idempotency_key` MUST
   produce one logical message and return the same `message_id`; the second returns `duplicate: true` (C-21). The
   same key with a different body or a different recipient MUST be `conflict` (C-22). Keys are scoped to the sender
   session and MUST be retained at least as long as the message `[no case: B-9]`.
5. **Identity.** The adapter stamps `sender.principal_ref`, `sender.session_id`, `sender.session_name`,
   `sender.human_label`, `team_ref`, `hop_count` and `created_at` from its own authority (C-20); caller-supplied values
   for those members MUST be rejected (4.4.6, C-23). A caller cannot impersonate a session by supplying its id (C-24).
6. **Team isolation.** Every command operates within the profile's team. A session outside the team MUST NOT be
   listed (C-12, C-26) and cannot be messaged, watched, heartbeated, closed, resumed or drained, and its messages are
   unreadable. The error for a foreign id MUST be byte-identical to the error for an unknown id: `not_found` (C-25,
   C-26).
7. **Ownership.** `session heartbeat`, `session close`, `message watch`, `message receive`, `message ack`,
   `resume.session_id` and `sender_session_id` MUST require the session to be owned by the profile's principal;
   otherwise `not_found`, the same answer as for an unknown id (C-13, C-19, C-24, C-37). `unauthorized` is reserved
   for three cases: "authenticated but not an active member of the team" (including a principal whose membership was
   revoked, on every verb that touches the team, its sessions or their messages — with error JSON byte-identical for
   a team that does not exist, so there is no team-existence oracle; C-26, C-43), a refused watch join, and a rejected
   join secret (`team join` MUST return the same `unauthorized` text for a wrong secret, an unknown team and a banned
   principal; C-04).
8. **Leases.** A session is `offline` when `now > lease_until` or it is closed; `active` when the lease is valid and
   `activity` is `busy`; `idle` otherwise (C-10, C-14). `session close` is an optimisation; expiry is authoritative
   (C-14). `session close` MUST be idempotent (C-15). Heartbeat on a closed session and sending from a closed session
   MUST return `conflict` (C-15, C-31); sending **to** a closed recipient is accepted — the message waits for retention
   or resume (C-31). Two sessions registered with the same name are two sessions (C-11). `session register` with
   `resume.session_id` re-opens a closed or expired owned session in place: same id, pending messages kept, metadata
   updated, `resumed: true` (C-19). A resume of a session whose lease is valid and which is not closed MUST fail with
   `conflict` (`details.reason = "session_live"`) and leave the session unchanged (C-19b): two processes must never
   drain one inbox, and after `/clear` the harness's by-native map holds two native ids for one Brigade session (D9), so
   a `claude --resume` of the old native id while the original process still runs would otherwise re-open a live
   session; the harness then registers a fresh session and rewrites the by-native entry.
9. **Retention.** An adapter MUST retain an unacknowledged message for at least `retention.unacked_message_seconds`
   `[no case: B-10]`; it MAY delete an acknowledged message after `retention.acked_message_seconds`, and MAY delete a
   closed or expired session after `retention.closed_session_seconds` together with its messages.
10. **Ordering.** None is guaranteed. Adapters SHOULD return catch-up batches oldest first (C-32, recorded and not
    asserted).
11. **Content.** `kind` is `text` only; `body` is non-empty UTF-8 of at most `max_body_bytes` bytes; `summary` at most
    `max_summary_chars`; names, labels and descriptions are capped by the `limits` member that governs each of them
    (the table in 4.4.1). All text is untrusted input at every layer, including the strings returned by `session
    list` and `team members`. Adapters MUST reject oversize input with `invalid_input` before persisting (C-16,
    C-27).
12. **Rate limits and loops.** Adapters MUST enforce a per-sender-session limit no looser than `limits.send_rate` and a
    per-principal limit, summed over every session of the principal, no looser than `limits.principal_send_rate`
    (C-28); MUST cap unacknowledged messages from one sender session to one recipient session at
    `max_unacked_per_sender_recipient` (`details.reason = "sender_quota_for_recipient"`), checked **before** the
    recipient-wide cap so that one sender cannot exhaust a recipient's inbox for everyone else (C-28); MUST cap
    unacknowledged messages per recipient at `max_unacked_per_recipient` (`details.reason = "recipient_inbox_full"`,
    C-28); and MUST return `rate_limited` with `retry_after_ms > 0` when a limit trips (C-28). `hop_count` is
    adapter-computed: `reply_to.hop_count + 1` when `reply_to` is given (`reply_to` MUST name a message the sender
    session received, else `not_found`; C-29); when `reply_to` is absent, one more than the `hop_count` of the most
    recent message the recipient session sent to the sender session within `implicit_reply_window_seconds` (an
    unlabelled answer is still an answer), and 0 when there is none (C-29b). `hop_count` increments by exactly one
    per hop (C-29, C-29b). A send whose `hop_count` would exceed `max_hop_count` MUST return `loop_detected` (C-29,
    C-29b). `rate_limited` and `loop_detected` are terminal for the model: `brigade send` never retries them.
13. **Version negotiation.** The harness runs `describe` once per adapter configuration and refuses to operate unless
    the `protocol_version` majors are equal (`protocol_mismatch`, exit 10; a harness-side outcome, so no adapter case).
    `describe.protocol_version` MUST be `"1"` for a v1 adapter (C-01). Features are discovered from `capabilities`,
    never inferred from `adapter.version` (C-18). Consumers parse with loose objects (C-17; JSON convention 2).
14. **Secrets.** No command output other than `team create` contains a secret (C-03, C-05); no secret is accepted on
    argv (`usage`, C-05); no secret appears in `describe` output or on stderr at any log level (C-05).
15. **No remote authority.** A message cannot grant permission, answer a prompt, change configuration, or represent
    human consent. This is restated in the injected frame, in the `brigade` command help and human-readable output,
    and in the skill.

## 4.6 Exit codes and error codes

| Exit | `error.code` | `retryable` | Meaning |
| --- | --- | --- | --- |
| 0 | (none) | | success |
| 1 | `internal` | `false` | unclassified failure (a bug); stack on stderr at debug |
| 2 | `usage` | `false` | bad argv: unknown group, verb or flag; a secret on argv |
| 3 | `invalid_input` | `false` | stdin missing, empty, over 1 MiB or failing the shape; oversize body, summary, name, label or description; a caller-supplied sender member; a malformed join secret; `details.field` names the member (4.3.1) |
| 4 | `unauthenticated` | `false` | no usable local credential, or the credential was revoked; run `team join` again |
| 5 | `unauthorized` | `false` | authenticated but not an active member of the team (including a revoked membership); watch join refused; join secret rejected (identical text for a wrong secret, an unknown team and a banned principal) |
| 6 | `not_found` | `false` | unknown, foreign or not-owned session or message id (uniform text) |
| 7 | `conflict` | `false` | idempotency key reused with a different payload; session closed; resume of a live session (`details.reason = "session_live"`); profile already bound to a team (`details.reason = "profile_bound"`); `profile init` on a configured profile without `--force` |
| 8 | `rate_limited` | `true` | `retry_after_ms` present; `details.reason` is one of `send_per_minute`, `send_per_hour`, `principal_per_minute`, `principal_per_hour`, `sender_quota_for_recipient`, `recipient_inbox_full`, `join_attempts`, `register_session`, `realtime` |
| 9 | `unavailable` | `true` | backend unreachable, 5xx, timeout, paused project (`details.reason = "project_paused"` when detectable) |
| 10 | `protocol_mismatch` | `false` | harness and adapter protocol majors differ |
| 11 | `config` | `false` | profile missing, invalid or world-readable; backend not configured; credential present but no team bound |
| 12 | `loop_detected` | `false` | `hop_count` cap reached |

The reference implementation also answers `usage` when stdin is a terminal on a command that reads a document, so a
human who forgets to pipe input is told rather than left hanging; this is a courtesy of `adapterkit.ReadInput`, not a
protocol obligation.

These twelve codes are the whole taxonomy (freeze item 7): an adapter maps every failure to one of them, and a code
the harness does not recognise is treated as `internal`. The exit status is a function of the code and nothing else;
the `retryable` column is the value an adapter sends (4.3). A `session` or `message` command on a profile that is not
bound to a team exits 4 `unauthenticated` (no credential) or 11 `config` (credential present, no team), documented per
adapter, and never with a stack trace (C-06, C-08). Adapters never exit 126, 127 or ≥ 128 from their own code
`[no case: B-11]`.

**Harness mapping (informative for adapter authors; it is what `internal/adapterkit.Spawn` does).** The harness maps
a child killed by a signal to `unavailable` with `details.signal` naming the signal; a timeout to `unavailable` with
`details.reason = "timeout"` (detected with `ctx.Err()`, because `cmd.Wait` reports the SIGTERM death the cancel
itself caused rather than the deadline); and a **missing executable** to `unavailable` with `details.reason =
"adapter_not_found"`, detected with `errors.Is(err, os.ErrNotExist) || errors.Is(err, exec.ErrNotFound)` — the second
half is not optional: `exec.ErrNotFound`, which a PATH search returns for a bare command name, does not wrap
`fs.ErrNotExist` (measured on go1.27.0), so the `ErrNotExist` predicate alone catches only an absolute-path miss and
would send an adapter that is merely not on `PATH` to `internal`. Stdout past 4 MiB (the child is cancelled), stdout
that is not one JSON document, and stdout that is not a valid 4.3 envelope all map to `internal` (`details.reason`
`stdout_overflow`, `stdout_not_json`, `stdout_invalid_envelope`). The harness never cross-checks an adapter's exit
status against its envelope's code: an adapter that exits with its own 4.6 status and a well-formed error envelope is
speaking the protocol. Plugin hook entrypoints translate every adapter failure to hook exit 0 with a diagnostic line
(exit 2 from the `UserPromptSubmit` hook would block and erase the user's prompt), so nothing surfaces as a hook error
and no prompt is ever lost.

**Supabase adapter mapping (informative; owned by the adapter, plan 5.4).** The PostgREST error body is parsed first,
whatever the HTTP status: a `message` starting with `brigade:` names the code directly; otherwise SQLSTATE `28000` → 4,
`42501` → 5 (→ 4 when the status is 401, "no usable JWT"), `P0002` → 6, `23505` → 7, `57014` → 9,
`PGRST301`/`PGRST303` → 4 after one refresh; a non-PostgREST body with HTTP 5xx, a transport error or a TLS/CA
failure → 9; GoTrue `refresh_token_already_used` (after one re-read-and-retry), `refresh_token_not_found`,
`session_not_found` and `session_expired` → 4.

## 4.8 What the protocol deliberately does not say

How an adapter authenticates, stores credentials, represents membership or transports events; whether `team_ref` (or
any other identifier) is a UUID; what a profile file looks like; the shape of the secret half of a join secret; how
`delivery.ordering` values other than `none` behave; and anything on the logical plan's "do not freeze" list (plan
section 12), which this document neither designs, stubs nor reserves beyond a member name that already exists:

- task assignment;
- broadcast messaging (one recipient per message; `delivery_state` is the only member that would change);
- attachments or file transfer;
- typing indicators;
- threads or rich conversations (`reply_to` and `hop_count` exist only for reply addressing and loop control);
- total message ordering;
- remote permission approval (a message can never approve anything, 4.5.15);
- verified human identity (`human_label` stays unverified);
- administrative roles beyond the creator-only rotate/revoke/transfer of Phase 5 (named in 4.2 and 4.7 as a
  capability and three command names, nothing more).

## 4.9 Semantics of `injected` for the Claude Code harness

`injected` means "the frame was written to the session's inbox socket and the connection closed without error". The
socket sends nothing back; an explicit native `crossSessionInbound: refuse` drops the post with no signal to either
side. This is stated here so that no consumer reads `injected` as "read by Claude".
